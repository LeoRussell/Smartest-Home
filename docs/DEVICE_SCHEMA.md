# Schema устройства и аппаратная конфигурация

Здесь описан формат Schema, который Gateway принимает сейчас, и его связь с
аппаратной конфигурацией универсальной прошивки.

## Schema и аппаратная конфигурация — разные сущности

`Schema` описывает, что устройство предоставляет Gateway: логические
компоненты, параметры, действия, режимы, типы значений, права доступа и
подсказки для интерфейса. Schema не должна содержать назначения GPIO и
параметры конкретной разводки.

Аппаратная конфигурация описывает, как профиль прошивки реализует эти
логические компоненты: ID драйверов, GPIO, шины, адреса и интервалы опроса.
Универсальная прошивка в `esp32/universal` получает эту конфигурацию от
Gateway во время работы. Она содержит версию, хэш, логические ID, драйверы,
GPIO и настройки опроса. Пользовательская прошивка из `esp32/examples/led/src` может
по-прежнему выбирать GPIO при сборке и сама объявлять свою Schema.

## Версии Schema

- `format_version` задаёт формат документа Schema. Сейчас поддерживается
  значение `1`; старые прошивки могут его не указывать.
- `schema_version` в сообщении `hello` — версия содержимого Schema,
  объявленная прошивкой. В пользовательской прошивке её увеличивает автор
  при изменении Schema.
- Аппаратная конфигурация имеет отдельные версию, хэш и статус применения.
  Универсальная прошивка использует `schema_version = max(1, config_version)`
  для своей фактически применённой конфигурации. `format_version` документа
  Schema при этом остаётся `1`.

Сохранённая в Gateway конфигурация и принятая Schema могут временно иметь
разные версии: новая конфигурация ожидает доставки или подтверждения, а
карточка и команды используют последнюю подтверждённую Schema.

Gateway принимает формат Schema 1 и прежний формат без `format_version`.
Перед сохранением и использованием он проверяет все объявленные поля.

## Что объявлять в Schema

| Раздел | Назначение |
| --- | --- |
| `components` | Необязательные логические группы параметров: датчик, выход, исполнительный механизм |
| `parameters` | Читаемые значения и управляемые состояния с типами, единицами и ограничениями |
| `actions` | Разовые операции или запуск алгоритма устройства, при необходимости с аргументами |
| `capabilities` | Булевы признаки возможностей прошивки; сами по себе не выполняют действия |
| `modes` | Авторские режимы, ссылающиеся на действия и необязательный параметр статуса |

LED — обычный параметр устройства, если им нужно управлять. Специального типа
`led`, отдельной LED-колонки протокола или обязательной лампочки нет.
`identify` — действие поиска; оно может использовать тот же индикатор или
другой способ, который реализовала прошивка.

### Параметры

Минимальное описание параметра содержит `type` и `access`. Его ключ —
стабильный ID, который используют состояние, команды и сценарии. `label`
меняет подпись, но не ID.

| Тип | JSON-значение | Доступ |
| --- | --- | --- |
| `boolean` | `true` или `false` | `read_only` / `read_write` |
| `integer` | Целое число, например `42` | `read_only` / `read_write` |
| `number` | Конечное число, например `21.5` | `read_only` / `read_write` |
| `string` | Строка | `read_only` / `read_write` |
| `enum` | Значение из `options` с совпадающим JSON-типом | `read_only` / `read_write` |
| `json` | Произвольное корректное JSON-значение | Только `read_only`; не используется в выражениях Blockly |

Boolean `true` не равен числу `1`, а число `1` не равно строке `"1"`.
`NaN` и бесконечности не являются допустимыми числовыми показаниями.

| Поле | Смысл |
| --- | --- |
| `label` | Подпись до 80 символов; без неё используется ID |
| `description` | Необязательное пояснение до 240 символов |
| `component` | ID объявленного логического компонента |
| `unit` | Необязательная единица до 24 символов, например `°C`, `lx`, `%`, `raw` |
| `precision` | От 0 до 8 знаков для отображения; не преобразует измерение |
| `min`, `max` | Включительные числовые границы; для `integer` также целые |
| `step` | Положительный шаг; значение должно попадать на шаг от `min`, а без `min` — от 0 |
| `options` | Для `enum`: от 1 до 32 уникальных значений с подписями |
| `control` | Совместимый с типом вид управления по умолчанию, только для `read_write` |

`unit` — метаданные, а не формула калибровки. Пересчёт raw в физическую
величину выполняет прошивка или поддерживаемый драйвер универсального
профиля. Для boolean и текстового статуса единицу можно не задавать.
В универсальном профиле ограничения текста считаются в **байтах UTF-8**
для буферов ESP32: название до 80 байт и единица до 24 байт.

Пример параметров с единицами и перечислением:

```json
{
  "format_version": 1,
  "parameters": {
    "temperature": {
      "label": "Температура",
      "type": "number",
      "access": "read_only",
      "unit": "°C",
      "precision": 1,
      "min": -40,
      "max": 125
    },
    "display_page": {
      "label": "Страница дисплея",
      "type": "enum",
      "access": "read_write",
      "control": "select",
      "options": [
        {"label": "Часы", "value": "clock"},
        {"label": "Показания", "value": "sensors"}
      ]
    }
  },
  "actions": {}
}
```

В `options[].value` допустимы строки, целые числа и boolean; произвольные
объекты и дробные числа вариантами перечисления сейчас не являются.

### Отображение и пользовательский выбор вида

| `control` в Schema | Допустимый параметр |
| --- | --- |
| `toggle` | `boolean`, `read_write` |
| `slider` | `integer`/`number`, `read_write`, обе границы и `min < max` |
| `select` | `enum`, `read_write` |
| `input` | `integer`/`number`/`string`, `read_write` |

Без подсказки интерфейс выбирает вид автоматически. Пользователь может
открыть кнопку со стрелкой у контрола и выбрать доступный альтернативный вид.
Это предпочтение хранится в `parameter_ui_preferences` SQLite, применяется
поверх Schema и не меняет её версию, тип или доступ параметра.

Пользовательское «Список» (`list`) отличается от `control: "select"` в
Schema. Оно доступно для boolean и поддерживаемых значений 0/1: boolean
покажет Вкл/Выкл, числовой диапазон 0–1 с шагом 1 или соответствующий enum —
0/1 с сохранением исходных типов. Числовой ползунок можно заменить вводом
числа и обратно при наличии диапазона. Возврат к виду по умолчанию убирает
пользовательское переопределение. Недопустимые предпочтения после изменения
Schema удаляются сервером.

### Действия и аргументы

Ключ действия — его ID для `invoke`. Допустимы `label`, `description` и
`arguments`. Если аргументы не нужны, достаточно `{"label": "Название"}`.
Аргумент описывает `type`, необязательные `label`, `unit`, `precision`,
числовые границы/шаг, enum `options` и `required`. По умолчанию аргумент
обязателен; `required: false` разрешает его отсутствие, но не подставляет
значение автоматически. Необъявленные аргументы отклоняются.

```json
{
  "format_version": 1,
  "parameters": {},
  "actions": {
    "calibrate": {
      "label": "Калибровка",
      "arguments": {
        "offset": {"type": "number", "unit": "°C", "min": -5, "max": 5},
        "quick": {"type": "boolean", "required": false}
      }
    }
  }
}
```

Типы аргументов: `boolean`, `integer`, `number`, `string`, `enum`.
Объект `json` и выражения Blockly в аргументах действий сейчас не
поддерживаются: блок вызова передаёт заполненные значения формы.

### Возможности, поиск и авторские режимы

Например, Schema устройства с реализованным поиском и ночным режимом:

```json
{
  "format_version": 1,
  "capabilities": {"identify": true, "built_in_indicator": true},
  "parameters": {
    "night_active": {"type": "boolean", "access": "read_only"}
  },
  "actions": {
    "identify": {"label": "Найти устройство"},
    "mode_night_select": {"label": "Ночной режим"}
  },
  "modes": {
    "night": {
      "label": "Ночной режим",
      "operations": {"select": "mode_night_select"},
      "status_parameter": "night_active",
      "status_value": true
    }
  }
}
```

`capabilities.identify: true` требует действия `identify`. Признак
`built_in_indicator` сообщает о встроенном индикаторе; алгоритм его работы
реализует прошивка. `universal_profile` объявляет универсальный профиль.

В `modes.operations` допустимы `select`, `enable`, `disable`; каждое значение
ссылается на существующее действие. `status_parameter` и `status_value`
задаются вместе и описывают, по какому принятому значению считать режим
активным. `conflicts_with` — необязательный список других объявленных
режимов, без ссылки на самого себя. Это метаданные для представления режима;
взаимоисключение и фактическое переключение реализует ESP32.

Рабочая регистрация C++-режимов описана в
[руководстве автоматизаций](AUTOMATION.md#действия-и-прошивочные-режимы),
а обмен и обработчики — в
[руководстве собственной прошивки](ADVANCED_FIRMWARE.md).

### Ограничения документа

До 64 компонентов, 64 параметров, 32 действий, 32 аргументов на действие,
16 capabilities и 8 режимов. ID компонентов, параметров, действий и
аргументов: `[A-Za-z][A-Za-z0-9_.-]{0,63}`. ID режима — до 48 символов;
готовый C++-реестр LED-примера ограничивает их 47 символами.
Размер сериализованной Schema — до 60 КиБ; всё WebSocket-сообщение — до 64 КиБ.
Полностью пустая Schema без параметров, действий, режимов и capabilities
не проходит проверку; ненастроенная универсальная плата объявляет capability
`universal_profile`.

## Пример логического компонента

```json
{
  "format_version": 1,
  "components": {
    "status_led": {
      "label": "Встроенный индикатор",
      "category": "actuator",
      "description": "Индикатор платы, которым управляет прошивка."
    }
  },
  "parameters": {
    "led": {
      "label": "Индикатор",
      "description": "Включает или выключает индикатор платы.",
      "component": "status_led",
      "type": "boolean",
      "access": "read_write",
      "control": "toggle"
    }
  },
  "actions": {}
}
```

`components` — необязательная карта со стабильными логическими ID. Сейчас
допустимы категории `sensor`, `actuator`, `input`, `output` и `other`.
Параметр может ссылаться на один компонент; Gateway отклонит ссылку на
необъявленный ID. Параметры без компонента остаются совместимыми и
отображаются как раньше.

Описание параметра (`description`) необязательно. Существующие поля `unit`,
числовые границы, `step`, `precision`, варианты `options`, права доступа и
тип контрола сохраняют свои проверки и поведение. Только для чтения означает,
что параметр нельзя менять: метаданные отображения не дают права отправлять
команды.

## Совместимость с пользовательской прошивкой

Продвинутая прошивка может по-прежнему отправлять `parameters`, `actions`,
`capabilities` и `modes` в `hello`. Она может добавить логические компоненты,
не меняя обработку команд. Gateway хранит Schema в существующем поле
`devices.schema_json` и сохраняет снимки в `device_schema_history`, поэтому
эти метаданные не требуют миграции БД.

Для пользовательских прошивок есть общая ESP32-библиотека
[`GatewayClient`](ADVANCED_FIRMWARE.md): она подключает Wi-Fi и WebSocket,
оставляя формат Schema и обработку команд коду устройства.

Универсальный профиль строит Schema из принятых аппаратных компонентов.
Поддерживаемые драйверы и ограничения GPIO перечислены в
[`UNIVERSAL_FIRMWARE.md`](UNIVERSAL_FIRMWARE.md). GPIO не смешиваются со
стабильными ID устройства, компонентов или параметров.

В карточке устройства можно скачать принятую Schema в JSON-обёртке
`smartest-home-schema` версии 1. Для универсального устройства окно настройки
дополнительно импортирует и экспортирует аппаратную конфигурацию. Gateway
проверяет импорт по реестру драйверов, а ESP32 подтверждает применение.

Schema из карточки — описание принятого интерфейса устройства. Экспорт из
конструктора универсальной платы — документ `smartest-home-device` с
`hardware_configuration` и `ui_preferences`; его можно импортировать в
конструктор. Одна логическая Schema не содержит назначений GPIO и не
заменяет аппаратную конфигурацию или файл `device_configuration.generated.h`.

Gateway сравнивает Schema по содержимому. Изменение без увеличения
`schema_version` всё равно вызывает предложение. Отказ сохраняет прежнюю
Schema и не добавляет новые параметры; при следующем подключении с тем же
отличием предложение появится снова. Восстановление снимка в истории
разрешено при отключённой плате и меняет только принятую Schema Gateway,
а не код или аппаратную конфигурацию ESP32. Удаление снимка из истории
не удаляет текущую Schema.

## Обмен универсальной прошивки с Gateway

Обмен идёт через один WebSocket. Логический ID в интерфейсе Gateway может
отличаться от исходного ID прошивки после переименования; сообщения ESP32
содержат исходный `UNIVERSAL_DEVICE_ID`, а Gateway сопоставляет оба ID.

| Отправитель | Сообщение | Что означает |
| --- | --- | --- |
| ESP32 | `hello` с `device_profile: "universal"`, `board_profile: "esp32-s3-devkitc-1"`, `driver_catalog`, `schema_version` и `schema` | Объявление профиля и фактически доступной Schema. Без конфигурации Schema содержит пустые `components`, `parameters`, `actions` и capability `universal_profile` |
| Gateway | `hello_ack` | Подключение разрешено. Универсальная прошивка начинает отправлять состояние и принимать команды после этого сообщения |
| Gateway | `device_config_request` | Запрос сохранённой в ESP32 конфигурации, когда в Gateway нет своего документа |
| ESP32 | `device_config_report` | Содержит `device`, `config_version`, `config_hash`, `schema_version`, `schema`, `configuration`. Без конфигурации версия равна `0`, хэш пустой, Schema имеет версию `1` |
| Gateway | `device_config_apply` | Содержит исходный `device`, `config_version`, `config_hash` и аппаратный документ `configuration` |
| ESP32 | `device_config_result` | Содержит исходный `device`, попытанные `config_version`/`config_hash`, `success`, фактические `schema_version`/`schema`; при отказе добавляется `error` |
| ESP32 | `state` | После регистрации передаёт `data.parameters` с логическими ID параметров. Входы опрашиваются с заданным интервалом; изменения и heartbeat отправляются по действующему соединению |

Версия аппаратной конфигурации — целое без знака, от 1 до 4294967295.
Хэш — SHA-256 от UTF-8 JSON аппаратной конфигурации с отсортированными ключами,
без пробелов между элементами и без ASCII-экранирования Unicode. Gateway
сохраняет именно такой JSON и передаёт поля в том же порядке. Массив
компонентов сохраняет свой порядок. Вид элемента интерфейса хранится отдельно
и в аппаратный хэш не входит.

ESP32 проверяет тело документа и хэш также при повторной отправке. Совпадение
заголовка с уже применённой версией не позволяет пропустить проверку тела.
Повтор корректного документа с теми же версией и хэшем подтверждается без
новой записи в NVS и без перенастройки GPIO. При отрицательном ответе Gateway
сохраняет принятую Schema предыдущей версии; `schema_version` в таком ответе
может отличаться от номера неудачной попытки `config_version`.

Подтверждение новой конфигурации принимается после совпадения версии и хэша
с сохранённой попыткой и проверки присланной Schema. Ответ от предыдущей
версии не подтверждает новую. Когда Gateway ещё не хранит аппаратный документ,
отчёт ESP32 может восстановить его только после разрешения подключения и
проверки поддерживаемых драйверов, GPIO, хэша и Schema.

Для применения действуют статусы `pending`, `applying`, `applied`, `failed`.
`pending` означает ожидание подключения, `applying` — ожидание ACK,
`applied` — подтверждённую версию, `failed` — отказ или истечение 20 секунд
ожидания. Сохранённая версия и последняя применённая версия отображаются
отдельно. Действие браузера `retry_device_configuration` содержит `device`
и необязательный `request_id`; ответ `device_configuration_retry_result`
возвращает `success`, `status`, `config_version`, `message` и тот же
`request_id`. Повторная отправка не создаёт новую аппаратную версию.

## Следующий этап

Дальше можно расширить реестр подтверждёнными драйверами для конкретных
датчиков и шин. Неизвестный датчик не считается поддержанным, пока его
обработчик не добавлен в универсальную прошивку и не проверен.
