# Автоматизация IoT Gateway

Редактор на Blockly собирает программу из соединённых блоков. Браузер сохраняет JSON-представление рабочей области и ограниченную программу в SQLite через Gateway. Исполнение происходит в Gateway и продолжается после закрытия вкладки. Gateway принимает декларативную JSON-программу, проверяет типы, доступ и ограничения Schema, затем обрабатывает её интерпретатором. Произвольный JavaScript или Python из браузера не запускается.

## Как собрать первый сценарий

Сначала подключите устройство, примите его Schema и проверьте ручное
управление. У универсальной платы до этого сохраните и примените аппаратную
конфигурацию. Blockly показывает только объявленные параметры и действия:
название модели `ESP32-S3` не является ID устройства. В списках используются
реальные ID Gateway, например `esp32-01`.

Пример: после включения `esp32-01.led` выключить его через пять секунд.

1. Во вкладке «Автоматизация» задайте название, например «Автовыключение».
2. Перетащите из «События» блок «Когда изменилось значение», выберите
   `esp32-01` и параметр светодиода.
3. Задайте фильтр «стало равно» → `истина`. «Без новых изменений» и
   «Пауза после запуска» оставьте равными 0.
4. Подсоедините снизу «подождать 5 секунд», затем «установить параметр» для
   того же устройства/параметра со значением `ложь`.
5. Нажмите «Проверить сценарий», затем «Сохранить сценарий». Проверка ничего
   не выполняет. Убедитесь, что сохранённый сценарий включён.
6. Включите лампу вручную и откройте историю запусков сценария.

Это пример для boolean-параметра. Для integer или enum 0/1 используйте
значения его Schema: число `1`, строка `"1"` и boolean `истина` различаются.

В рабочей области должен быть **один верхний блок события** и связанная с ним
цепочка действий. Свободно лежащий дополнительный блок мешает сохранению:
подсоедините его или удалите. «Отменить изменение» и «Вернуть изменение»
относятся к блокам редактора; они не откатывают выполненные команды устройств.
Очистка блоков сама по себе не удаляет сохранённый сценарий из БД.

## Доступные блоки

- Запуск при изменении параметра (при любом изменении или только при переходе к выбранному значению), подключении или отключении устройства, старте Gateway.
- Чтение параметра устройства и проверка соединения.
- Сравнение значений, блоки И/ИЛИ/НЕ, ветвления ЕСЛИ/ИНАЧЕ и последовательность действий.
- Установка объявленного в Schema параметра `read_write`.
- Вызов объявленного устройством `schema.actions`, в том числе действий с типизированными аргументами.
- Арифметические выражения (+, −, ×, ÷ и степень) в значениях и условиях.
- Пауза от 0 до 3600 секунд; остановка сценария проверяется во время ожидания.
- Выбор режима, объявленного прошивкой, и вызов поддерживаемой для него операции.

Списки устройств, параметров и действий строятся по Schema, а не зашиваются в редактор. У блока изменения параметра можно оставить запуск на любое новое значение или выбрать точное значение, к которому параметр должен измениться. Для boolean и enum доступны значения из Schema; числа и текст вводятся в самом блоке. Gateway проверяет фильтр по типу и ограничениям Schema при сохранении и снова при запуске. Старые сценарии без фильтра продолжают запускаться при любом изменении параметра.

Например, для сценария «включить лампу на пять секунд» задайте запуск при изменении `esp32-01.led` со значением `true`, затем добавьте паузу и выключение. Выключение лампы больше не запустит этот сценарий заново, а повторное включение начнёт новый полный отсчёт.

Блок «текущее значение параметра» возвращает само значение: число, строку
или boolean. Он нужен внутри вычисления, сравнения или значения команды.
Блок «значение параметра … равно …» уже возвращает boolean и подходит в
условие ЕСЛИ. Параметры `json` в этих блоках не используются.

«Нет доступных параметров» означает, что в принятой Schema нет подходящего
параметра для данного блока. В блоке установки нужны `read_write`, а в
чтении/событии — читаемые параметры поддерживаемого типа. Проверьте выбранное
устройство, подтверждение Schema и результат применения конфигурации.

### Устойчивость, пауза между запусками и повторный запуск

У события изменения есть две разные настройки:

| Настройка | Поведение |
| --- | --- |
| «Без новых изменений» | 0–3600 целых секунд. После изменения Gateway ждёт, чтобы параметр оставался тем же; новое изменение отменяет прежнее ожидание |
| «Пауза после запуска» | 0–86400 целых секунд между началами запусков. Подходящее событие внутри этого интервала может ждать его окончания, пока значение остаётся тем же и свежим |

Обе проверки требуют актуального показания к моменту запуска. При
отключении устройства, отключении сценария или изменении его триггера
ожидающий запуск отменяется. Обычные одинаковые отчёты обновляют свежесть,
но не перезапускают таймер устойчивости.

«Без новых изменений» проверяет стабильность **значения параметра**, а не
истинность произвольного условия ЕСЛИ. Например, колебания ADC с 10 на 11
начнут ожидание заново, даже если оба значения ниже выбранного порога.

Если сценарий уже исполняет блок «подождать», новое подходящее срабатывание
прерывает старый запуск и начинает сценарий с начала. Поэтому для
автовыключения повторное включение после выключения даёт полные новые пять
секунд. Уже отправленную команду это не отзывает. Пока сценарий выполняет
команду, параллельный второй запуск того же сценария не создаётся.

## Имя устройства и ID

В карточке устройства отображаемое имя можно менять отдельно от ID. Имя используется для удобства в интерфейсе, а выпадающие списки Blockly показывают ID Gateway и сохраняют именно его. ID должен быть уникальным и соответствовать формату `A-Z`, `a-z`, `0-9`, дефис или подчёркивание; он начинается с буквы.

Gateway запоминает связь изменённого ID с исходным ID прошивки, поэтому ESP32 не нужно перепрошивать после переименования. Имя можно менять на подключённом устройстве; смена ID доступна после отключения. Сохранённые автоматизации, очередь команд, история событий и Schema переезжают на новый ID вместе с устройством.

## Гистерезис

Можно собрать два отдельных условия в одной программе:

```text
КОГДА изменилось значение sensor.illuminance
  ЕСЛИ illuminance < 30
    УСТАНОВИТЬ lamp.relay = true
  ЕСЛИ illuminance > 50
    УСТАНОВИТЬ lamp.relay = false
```

Между 30 и 50 состояние реле не меняется. Каждый блок условия проверяется при изменении параметра запускающего датчика; одинаковые повторные отчёты не запускают сценарий заново.

Изменение учитывается как в сообщениях состояния от устройства, так и в подтверждённом результате команды Gateway. Если последующее сообщение состояния повторяет уже учтённое значение, второй запуск не создаётся.

## Исполнение и ошибки

Перед сохранением можно нажать «Проверить сценарий» под редактором. Та же
проверка доступна кнопкой «Проверить» в карточке сохранённого сценария.
Gateway проверяет ссылки на Schema, доступность устройств для команд и
свежесть показаний, используемых в условиях. Проверка не запускает сценарий
и не отправляет устройствам команды. Ссылка возле сообщения открывает
соответствующее устройство. Результат описывает состояние на момент проверки;
после изменения блоков нужно повторить проверку.

Список сценариев можно искать по названию или ID устройства и фильтровать:
включённые, отключённые и требующие внимания. Последний фильтр учитывает
ошибки последнего запуска и замечания выполненной проверки.

Команды выполняются по порядку, Gateway ждёт подтверждение каждого действия и останавливает оставшуюся последовательность при ошибке. Состояние, последний результат и текст ошибки видны в списке сценариев. Остановка сценария завершается после текущей команды. При чтении параметра Gateway требует свежие данные от подключённого в текущей сессии устройства; кэш из прошлой сессии не считается текущим показанием.

Свежесть учитывается отдельно для каждого параметра: обновление одного
показания не продлевает срок актуальности остальных. Пустой heartbeat и
WebSocket ping/pong подтверждают связь, но не обновляют показания.

В журнале событий успешная команда сценария отображается только через
фактическое изменение состояния. Повторяющегося «Результата команды» нет;
если значение не изменилось, новое событие состояния не создаётся.
Подробности выполнения остаются в истории запуска сценария. Ошибки команд
видны в журнале. Это правило действует также для старой истории,
уведомлений и экспорта CSV; исходные старые записи в базе сохраняются.

У универсального устройства событие подключения ожидает подтверждения
аппаратной конфигурации и первого актуального состояния. Поэтому сценарий
подключения читает параметры уже подтверждённой конфигурации. Во время её
применения управление и запуск по промежуточной телеметрии приостановлены.

Для каждого сценария Gateway сохраняет до 50 последних запусков: событие запуска, результат, проверки условий, паузы, команды и ошибки шагов. История загружается по запросу при раскрытии карточки. Перезапуск Gateway помечает незавершённый запуск как прерванный; удаление сценария удаляет и его историю.

В карточке сценария можно включить/отключить его, открыть на редактирование,
проверить или удалить. Для выполняющегося сценария доступна остановка:
ожидание прерывается, а уже отправленная команда завершает текущий шаг.
После перезапуска Gateway старые паузы не продолжаются; новые события снова
могут запускать включённые сценарии. Событие «При запуске Gateway» не
ожидает подключения всех устройств — проверьте доступность в самом сценарии
или используйте событие подключения нужного устройства.

В истории есть результат запуска, условия и отдельные шаги. Завершённую
запись можно удалить, а историю сценария — очистить целиком с подтверждением;
выполняющийся запуск сохраняется. Кнопка `>>` в связанном событии открывает
конкретный запуск. Удаление истории не меняет блоки сценария.

Если Schema устройства изменилась и блок больше не соответствует объявленным возможностям, правило не выполнится и в статусе сценария появится причина. Сценарий сохраняется, чтобы его можно было исправить.

## Действия и прошивочные режимы

Прошивка объявляет готовые режимы в отдельном реестре `deviceModes` в `esp32/examples/led/src/DeviceModes.cpp`. Каждый режим получает стабильный ID и название, а флаги `MODE_CAN_SELECT`, `MODE_CAN_ENABLE` и `MODE_CAN_DISABLE` разрешают только операции с обработчиками. Обработчик возвращает `true`, если выполнил операцию. `DeviceSchema.cpp` публикует режимы в `schema.modes` и формирует соответствующие действия в `schema.actions`; `main.cpp` передаёт команду зарегистрированному обработчику. Устройство без записей в реестре отправляет Schema без режимов; список в интерфейсе остаётся пустым.

Пример регистрации (замените функции на уже реализованные алгоритмы своего устройства):

```cpp
bool runNightMode(String& error);
bool enableNightMode(String& error);
bool disableNightMode(String& error);
bool isNightModeActive();
const char* nightConflicts[] = {"day", nullptr};

const DeviceModeRegistration deviceModes[] = {
    {
        "night", "Ночной режим", "Приглушённая яркость и обновление экрана",
        MODE_CAN_SELECT | MODE_CAN_ENABLE | MODE_CAN_DISABLE,
        runNightMode, enableNightMode, disableNightMode,
        nightConflicts, "night_active", true, isNightModeActive
    },
    {nullptr, nullptr, nullptr, 0, nullptr, nullptr, nullptr, nullptr,
     nullptr, false, nullptr}
};
```

Шаблонный реестр пуст. Замените пустую завершающую запись своим режимом и
реализуйте функции рядом с аппаратной логикой. Операции без флага и обработчика
не попадают в Schema. `isNightModeActive` — необязательный источник статуса:
устройство объявляет его как read-only boolean и передаёт в телеметрии.
Алгоритм режима остаётся в прошивке; Gateway вызывает только объявленные
операции. Для операции с аргументами добавьте описание действия в
`DeviceSchema.cpp`, а обработку — в `main.cpp`. В примере `nightConflicts`
ссылается на режим `day`, который должен быть зарегистрирован отдельно;
несуществующие ссылки прошивка пропускает.

## Ограничения и устройство системы

Редактор поддерживает вложенные условия и последовательности действий.
Циклов, переменных, календарного расписания и произвольного C++/Python-кода
в сценарии сейчас нет. Аргументы вызова действия задаются в его форме;
числовые выражения можно использовать для установки параметра, с учётом
типа результата. Деление на ноль или выход результата за Schema завершает
запуск ошибкой. Для записи в `integer` выражение также должно иметь
совместимый тип; арифметика типизируется как `number`.

Одна программа содержит до 200 узлов с вложенностью до 20, до 100 действий
в ветке, до 6 ветвей ЕСЛИ и до 16 операндов И/ИЛИ. Пауза — до 3600 секунд,
сериализованный документ сценария — до 48 КиБ.

Gateway хранит документ сценария `version: 2`: имя, состояние рабочей области
Blockly (`workspace`) и проверяемую программу (`program`, версия 1).
Это версии формата сценариев, независимые от версий Schema и прошивки.
Старые пороговые сценарии поддерживаются для совместимости и переводятся
редактором в блоки при редактировании.

Чтобы добавить новый тип блока, согласованно измените определение и разбор
в `web/automation-blockly.js`, проверку программы и исполнение в
`gateway/main.py`, а затем добавьте проверки корректного и ошибочного
поведения в `gateway/tests/`. Сохраняйте совместимость сериализованной рабочей
области: удаление типа блока может сделать сохранённый сценарий недоступным
редактору.

Авторские алгоритмы на ESP32 и серверные сценарии дополняют друг друга.
Например, C++-режим выводит сложный интерфейс на дисплей, а Blockly выбирает
этот режим при изменении датчика. Начало разработки собственной прошивки
описано в [ADVANCED_FIRMWARE.md](ADVANCED_FIRMWARE.md), типы параметров и
режимов — в [DEVICE_SCHEMA.md](DEVICE_SCHEMA.md).
