# Универсальная прошивка ESP32

Универсальный профиль позволяет настроить несколько простых GPIO-компонентов
через Gateway без собственного кода для каждого компонента. Сейчас он
поддерживает цифровой выход, цифровой вход, аналоговый вход ADC и PWM-выход.
Подключение неизвестного датчика само по себе не добавляет драйвер: Gateway
показывает только типы, которые прошивка действительно умеет обрабатывать.

Сетевой запуск находится в `esp32/universal/src/main.cpp`, реализация
компонентов — в `src/UniversalDevice.cpp`, а ID и имя — в
`include/user_config.h`. Загружать нужно весь PlatformIO-проект, а не один
`main.cpp`: он использует остальные файлы и общий `GatewayClient`.
Назначение файлов обоих вариантов описано в [esp32/README.md](../esp32/README.md).

## Подготовка и загрузка

1. Скопируйте `esp32/shared/include/secrets.example.h` в `esp32/shared/include/secrets.h`.
   Укажите Wi-Fi и фактический IP компьютера с Gateway, например `192.168.0.102`.
2. В `esp32/universal/include/user_config.h` задайте уникальный
   `UNIVERSAL_DEVICE_ID` каждой плате. Для нескольких устройств используйте,
   например, `esp32-01`, `esp32-02`. Отображаемое имя можно менять отдельно.
3. Подключите ESP32-S3 DevKitC-1 и из корня проекта соберите прошивку:

   ```powershell
   pio run -d esp32/universal
   pio run -d esp32/universal -t upload
   pio device monitor -d esp32/universal
   ```

   Профиль использует общий `GatewayClient` из `esp32/shared/lib/GatewayClient`
   и `secrets.h` из `esp32/shared/include`. Пользовательская прошивка с
   собственной Schema и C++-режимами находится в `esp32/examples/led`.
4. Подключите плату к Gateway и разрешите её подключение в окне запроса.
   Кнопка «Настроить» в карточке устройства появляется для универсального
   профиля.

### Первый запуск через интерфейс

1. Загрузите базовую прошивку. Файл `device_configuration.generated.h` для
   первого подключения не нужен: без сохранённой конфигурации прошивка
   объявляет пустую Schema и не назначает GPIO компонентам.
2. Разрешите подключение в Gateway. До `hello_ack` устройство отправляет
   только `hello`; состояние и обработка команд начинаются после разрешения.
   При повторном подключении выбор запрашивается снова, если его не запомнили.
3. Нажмите «Настроить». Выберите «Добавить из шаблона» или «Добавить компонент»
   и задайте логические ID, название, драйвер, GPIO и его параметры. Шаблон
   заполняет поля для поддерживаемого драйвера; физически подключённый модуль
   прошивка не определяет. Например, реле использует обычный цифровой выход.
4. Проверьте «Предпросмотр карточки». Это представление будущей Schema;
   изменение предпросмотра не отправляет команды устройству. Ошибки ID,
   диапазонов и занятых GPIO показываются у соответствующих полей.
5. Нажмите «Сохранить и применить». Gateway проверяет документ, сохраняет его
   и отправляет ESP32. Новая Schema становится принятой после положительного
   подтверждения устройства. До этого строка «Сохранено в Gateway» может
   показывать новую версию, а «Подтверждено ESP32» — предыдущую.
6. После подтверждения управляемые параметры появляются в карточке, а входы
   и выходы становятся доступны блокам автоматизации. Для типовой настройки
   повторно прошивать ESP32 не требуется.

Конструктор можно заполнять при отключённой ESP32, если Gateway работает и
устройство уже известно ему. Сохранённые изменения останутся в ожидании и
отправятся при следующем разрешённом подключении. После ошибки или потери
подтверждения используйте «Повторить сохранённую»: отправится та же версия,
черновик в окне при этом сохраняется. «Вернуть сохранённую» заменяет черновик
последней сохранённой конфигурацией после подтверждения пользователя.
Импорт, экспорт JSON, скачивание Schema и файла `.h` находятся в разделе
«Файлы и перенос конфигурации».

## Поддерживаемые компоненты

| Драйвер | ID в конфигурации | Что передаёт | GPIO и ограничения |
| --- | --- | --- | --- |
| Цифровой выход | `gpio_output` | Boolean, доступен командам | HIGH/LOW; активный уровень и начальное состояние настраиваются |
| Цифровой вход | `digital_input` | Boolean только для чтения | Подтяжка none/up/down, опрос от 100 мс |
| Аналоговый вход (ADC) | `analog_input` | Масштабируемое целое значение, только чтение | ADC GPIO 1, 2, 4–10, опрос от 250 мс; линейная калибровка raw и итогового диапазона |
| PWM-выход | `pwm_output` | Integer в выбранном диапазоне, доступен командам | Диапазон настраивается внутри 0–255; переключение между ползунком и вводом числа |

Одно устройство поддерживает до восьми компонентов плюс отдельный индикатор
`identify`. Интервал цифрового входа — 100–60000 мс, ADC — 250–60000 мс.
ADC использует 12-битный raw-диапазон 0–4095; итоговые границы задаются внутри
−1000000…1000000 и должны возрастать. Значения за raw-границами ограничиваются
ближайшей границей, результат линейного пересчёта округляется до целого.
Единица измерения — подпись, например `lx` или `°C`; сама по себе она не
превращает raw-показание в физическую величину. Без заданной единицы используется
`raw`. PWM работает с частотой 1 кГц и разрешением 8 бит; значения и начальное
значение должны укладываться в выбранные границы 0–255.

Для этого профиля Gateway и прошивка принимают GPIO 1, 2, 4–18 и 21. Они
отклоняют GPIO загрузочных strapping-пинов, USB, flash/PSRAM и GPIO 38/48:
встроенный RGB-индикатор DevKitC-1 использует один из последних пинов в
зависимости от ревизии. Дублировать физический пин между компонентами нельзя.
Проверка не может определить внешние перемычки и подключённые модули, поэтому
перед сохранением сверяйте распиновку именно своей платы.

Это ограничение универсального профиля. В LED-примере обычный GPIO-светодиод
на GPIO 48 разрешён его собственным кодом; в универсальном конструкторе GPIO
38/48 доступны только как NeoPixel-индикатор поиска. Не выбирайте NeoPixel
для обычного внешнего LED: это другой электрический протокол.

GPIO ESP32 рассчитаны на логический уровень 3.3 V. Не подключайте к ним
сетевое напряжение, мотор или нагрузку, превышающую возможности вывода:
используйте подходящий драйвер или модуль реле. Для ADC задайте крайние raw
показания и соответствующий им итоговый диапазон. Прошивка линейно преобразует
значение и ограничивает его выбранными границами. Это удобно для простой
калибровки, но не заменяет драйвер конкретного датчика: например, для нелинейного
фоторезистора или датчика температуры нужна отдельная формула/библиотека.

## Настройка и автоматизация

В конструкторе задайте уникальные латинские ID компонента и параметра,
названия, драйвер, GPIO и его настройки. Например:

```json
{
  "format_version": 1,
  "components": [
    {
      "id": "desk_lamp",
      "driver": "gpio_output",
      "label": "Настольная лампа",
      "parameter_id": "enabled",
      "parameter_label": "Включена",
      "pin": 4,
      "active_high": true,
      "initial_value": false
    },
    {
      "id": "light_sensor",
      "driver": "analog_input",
      "label": "Датчик освещения",
      "parameter_id": "light_raw",
      "parameter_label": "Уровень освещения",
      "pin": 5,
      "interval_ms": 1000,
      "unit": "lx",
      "raw_min": 200,
      "raw_max": 3900,
      "value_min": 0,
      "value_max": 1200
    }
  ]
}
```

Это аппаратная конфигурация, а не логическая Schema: поле `components` здесь
массив с GPIO и драйверами. Для примера подразумевается обычный выход на GPIO
4 и аналоговый вход на GPIO 5. Числа калибровки приведены для демонстрации;
чтобы показывать настоящие люксы, измерьте и обоснуйте соответствие датчика.
Если такой калибровки нет, оставьте единицу `raw` и диапазон отсчётов ADC.

Gateway проверяет драйверы, IDs, ограничения значений, интервалы, GPIO и
конфликты до сохранения. Названия должны занимать не более 80 байт UTF-8,
единица измерения — не более 24 байт, чтобы гарантированно поместиться в
буферы прошивки. ID компонента и параметра состоят из 1–64 латинских букв,
цифр, `_`, `-` или `.`, начинаются с буквы и уникальны внутри устройства.
Нормализованный аппаратный JSON должен помещаться в 3000 байт UTF-8.
У PWM можно задать допустимые min/max в пределах 0–255 и
начальное значение внутри этого диапазона. Для управляемых выходов настройка
также сохраняет вид элемента отдельно от аппаратной конфигурации; её можно
поменять позднее в карточке устройства. Schema создаётся из аппаратной
конфигурации; те же параметры сразу доступны в карточке устройства и в Blockly. Для изменения
логики сравнения или управления устройством используйте серверные сценарии
автоматизации.

Пользовательское имя/ID устройства, ID компонента и ID параметра — разные
вещи. Например, устройство `esp32-01` содержит компонент `desk_lamp`, а его
управляемый параметр называется `enabled`. В Blockly выбираются
`esp32-01` и `enabled`, а подписью может быть «Настольная лампа / Включена».
Смена ID параметра создаёт другую ссылку: проверьте ранее сохранённые сценарии.

Универсальная прошивка сама по себе не объявляет авторских C++-режимов,
поэтому список «Сценарий устройства» может быть пустым. Это отдельный список
режимов из `schema.modes`, а не список серверных сценариев Blockly.
Сложные алгоритмы и свои режимы реализуются
[пользовательской прошивкой](ADVANCED_FIRMWARE.md).

Внизу конструктора можно отдельно назначить индикатор действия «Найти
устройство». Обычный светодиод задаётся GPIO и активным уровнем; встроенный
адресный индикатор ESP32-S3 выбирается как NeoPixel на GPIO 38 или 48 с
настраиваемой яркостью. Выберите фактический пин своей ревизии платы. Этот
индикатор не занимает слот параметра и не становится отдельной LED-командой:
он только добавляет действие `identify` в Schema. Отметка «Считать встроенным
индикатором» отдельно управляет capability `built_in_indicator`. Если индикатор
не выбран, действие не публикуется.

## Применение, сохранение и восстановление

Gateway является основным источником конфигурации и хранит её версию, хэш,
статус и историю в SQLite. JSON-экспорт вместе с принятой Schema записывается
в `schemas/<ID>.json` рядом с файлом базы данных (по умолчанию
`gateway/schemas/<ID>.json`); из окна настройки можно скачать JSON. Папку
Gateway браузер напрямую не открывает, поэтому интерфейс показывает путь и
предлагает скачать файл. Импорт сначала проверяется, а затем применяется
только после подтверждения ESP32.

| Кнопка/файл | Содержимое и назначение |
| --- | --- |
| «Экспорт JSON» в конструкторе | Текущий черновик аппаратной конфигурации и предпочтений UI; может отличаться от сохранённого |
| «Скачать Schema из Gateway» в конструкторе | Сохранённый документ `smartest-home-device` из `schemas/<ID>.json`, с аппаратной конфигурацией, принятой Schema и статусом |
| «Скачать текущую Schema» в истории карточки | Только принятая логическая Schema в обёртке `smartest-home-schema`; GPIO не содержит |
| «Файл для прошивки (.h)» | Начальная аппаратная конфигурация для включения в сборку |
| Резервная копия `.sqlite3` | Вся база Gateway, включая события, доступ и автоматизации; создаётся в настройках |

«Импорт JSON» принимает аппаратный документ версии 1 или его обёртку с
`hardware_configuration`/`configuration`. Импорт заполняет черновик;
для применения нажмите «Сохранить и применить». Скачать файл и применить его
к плате — разные операции. Свежая схема из карточки без аппаратных данных
не подходит для восстановления GPIO.

Есть два способа доставить конфигурацию в универсальную прошивку:

1. **Динамический — основной.** Сохраните конфигурацию в Gateway. Он отправит
   её подключённой ESP32; при отключённой плате — при следующем подключении.
   Для обычных изменений повторно собирать и загружать прошивку не нужно.
2. **Встроенный файл — по желанию.** После сохранения нажмите «Файл для
   прошивки (.h)», скопируйте скачанный `device_configuration.generated.h` в
   `esp32/universal/include/` и прошейте плату. При первом запуске без записи в
   NVS прошивка применит этот снимок. Gateway всё равно остаётся основным
   хранилищем и при наличии своей сохранённой конфигурации синхронизирует её с
   устройством. У каждой платы должен быть свой `UNIVERSAL_DEVICE_ID` и свой
   сгенерированный файл.

Перед изменением ESP32 проверяет всю конфигурацию, допустимые GPIO, типы и
уникальность ресурсов, а также SHA-256 конфигурации. Ошибочный документ или
ошибка записи в NVS оставляет работающую конфигурацию и её выходы без изменений.
При успехе устройство сохраняет один согласованный пакет версии, хэша и
конфигурации в NVS, настраивает пины и отправляет Schema с подтверждением.
При загрузке из NVS документ также проверяется: если сохранённая запись
повреждена, прошивка стартует без настройки GPIO и ждёт рабочую конфигурацию
от Gateway.

Повтор того же документа с той же версией и хэшем проходит проверку и
подтверждается без записи в NVS, сброса выходов и остановки индикатора.
Версия изменяется только при сохранении изменённой аппаратной конфигурации;
повторная доставка и смена вида элемента интерфейса её не увеличивают.
Если за 20 секунд ESP32 не подтвердила применение, Gateway показывает ошибку,
сохраняя предыдущую принятую Schema. Повторную отправку можно запустить
из конструктора. Разрыв связи во время применения переводит сохранённую
конфигурацию в ожидание следующего подключения.

После перезапуска Gateway повторно отправляет сохранённую конфигурацию.
Если Gateway DB потеряна, он может восстановить конфигурацию из разрешённой
ESP32 после проверки хэша и Schema. Поля сообщений описаны в
[`DEVICE_SCHEMA.md`](DEVICE_SCHEMA.md#обмен-универсальной-прошивки-с-gateway).

Очередь команд и сценарии по событию подключения возобновляются после
проверенного подтверждения конфигурации и первого полного актуального
`state`. Пустой отчёт ненастроенной платы завершает синхронизацию сразу;
при восстановлении конфигурации из NVS Gateway может использовать уже
полученное полное состояние текущего подключения.

NVS хранит назначения пинов и настройки, включая начальные значения выходов.
Текущие значения, установленные командами, в NVS не записываются. Поэтому
полный перезапуск ESP32 устанавливает настроенные начальные значения;
переподключение WebSocket без перезапуска сохраняет текущие значения выходов.
Сохранённая NVS-конфигурация имеет приоритет над встроенным файлом `.h`.

Состояния датчиков отправляются при изменении и не реже одного раза в 10
секунд. Поддерживаемый список GPIO, ограничения и структура сообщений
определены в `gateway/device_configuration.py` и
`esp32/universal/src/UniversalDevice.cpp`. При добавлении драйвера обновляйте
оба реестра и тесты вместе.

Применение изменённой конфигурации перенастраивает GPIO. Для выхода с теми же
ID компонента, драйвером, пином и начальным значением прошивка сохраняет
текущее логическое значение; для PWM ограничивает его новыми границами.
Новый или переназначенный выход, а также изменение `initial_value` используют
настроенное начальное значение. Не используйте сохранение конфигурации
вместо обычной команды переключения. Изменение только вида контрола и повтор
того же аппаратного документа выходы не сбрасывают.

## Связь и диагностика переподключений

Общая библиотека `GatewayClient` оставляет повторное подключение Wi-Fi
драйверу ESP32. Параллельного таймера `WiFi.reconnect()` нет: этот вызов
принудительно разрывает Wi-Fi и мог прервать уже выполняющееся восстановление
связи или получение IP. Если точка доступа отсутствовала при запуске и
появилась позже, драйвер продолжает попытки по причине `NO_AP_FOUND`.
WebSocket обрабатывается только после получения Wi-Fi IP; при потере Wi-Fi
старое TCP-соединение закрывается, затем выполняется новый `hello`.

По умолчанию энергосбережение Wi-Fi отключено для постоянного соединения
и управления с малой задержкой. Это увеличивает потребление по сравнению
с modem sleep. Для устройства с приоритетом энергосбережения можно добавить
`-DGATEWAY_WIFI_POWER_SAVE=1` в `build_flags` своего профиля; на такой
настройке отдельно проверьте задержки и устойчивость связи с вашим роутером.

Проверку транспорта выполняет Gateway обычными WebSocket ping/pong.
Библиотека ESP32 отвечает на ping автоматически, пока вызывается
`gateway.loop()`. Отдельная конкурирующая политика ping-таймера на ESP32
не включена. Отсутствие нового значения датчика и потеря соединения — разные
состояния: ответившее на ping устройство может оставаться подключённым,
а его давно не обновлявшийся параметр требует новой телеметрии.

В профиле universal и трёх DevKitC-1 LED-профилях включён USB CDC для
встроенного USB Serial/JTAG ESP32-S3. Это позволяет увидеть `Serial` через
нативный USB-порт платы. Настройки Feather оставлены штатными. Прошивка не
ждёт открытия Serial Monitor или DTR, а ожидание записи в нативный USB
ограничено: отсутствие компьютера не должно останавливать обработку сети.
Если на плате остаётся предыдущая прошивка без CDC, новые логи появятся после
обычной загрузки обновлённой сборки.

Например, для платы на COM6 откройте монитор из корня проекта:

```powershell
pio device monitor -d esp32/universal --port COM6 --baud 115200
```

| Строка Serial Monitor | Что проверять |
| --- | --- |
| `[NET] startup reset_reason=…` | Повтор этой строки означает перезапуск ESP32. Причина сброса и `free_heap` помогают отличить перезапуск от простого разрыва WebSocket |
| `[NET] Wi-Fi disconnected … reason=… (…)` | Числовая и текстовая причины от Wi-Fi-драйвера, например `NO_AP_FOUND`, `BEACON_TIMEOUT` или `AUTH_FAIL`. При ошибке авторизации проверьте учётные данные сети |
| `[NET] Wi-Fi connected IP=…`, `rssi=…` | Актуальный локальный IP и уровень сигнала после восстановления. Пароль и SSID в эти логи не выводятся |
| `[NET] WebSocket disconnected connection=… wifi=…` | Время работы зарегистрированного WebSocket; `wifi=3` означает, что Wi-Fi по-прежнему подключён. `last_rx` включает ping/pong, `last_app_tx` относится к последнему JSON-сообщению приложения |
| `peer_reason=unavailable` | Установленная WebSockets-библиотека часто не передаёт RFC-код закрытия в callback. Сопоставьте время с кодом и причиной закрытия в консоли Gateway |
| `[NET] Gateway ping received` | Библиотека получила ping и обработала автоматический pong; доставку ответа и решение о закрытии контролирует Gateway |

Для проверки оставьте пустую универсальную плату подключённой на несколько
минут, затем повторите с настроенными входами. Отдельно отключите и верните
точку доступа и компьютер с Gateway: плата должна восстановить соединение
с новым `hello`, сохранив NVS-конфигурацию. GPIO при переподключении без
перезапуска сохраняют текущее логическое состояние. Реальную устойчивость
Wi-Fi, питание и уровень сигнала проверяют на самой плате; сборка и серверные
тесты не измеряют эти свойства.

## Ограничения текущего набора

Текущий профиль не реализует произвольные I²C/SPI/UART-датчики, нелинейные
формулы датчиков, интеграцию конкретных модулей, встроенные сценарии самой платы или
автоматическое обнаружение электрических соединений. Для новых типов датчиков
добавляется отдельный драйвер в универсальную прошивку. GPIO- и NeoPixel-индикатор
для команды «Найти устройство» настраивается вручную в конструкторе. Если требуется свой
алгоритм, действия или режим устройства, используйте пользовательскую
прошивку и протокол из [`ADVANCED_FIRMWARE.md`](ADVANCED_FIRMWARE.md).

## Ручная приёмка на ESP32

Автотесты в `gateway/tests/test_universal_lifecycle.py` используют временную
SQLite и сообщения тестовых WebSocket-устройств. Они проверяют серверный
протокол и сохранение данных; работу GPIO, ADC, PWM, Wi-Fi и NVS на реальной
плате проверяют следующие шаги. Для проверки восстановления используйте
отдельную тестовую БД.

| Проверка | Действия | Ожидаемый результат |
| --- | --- | --- |
| Пустая прошивка | Запустить плату без `.h` и без сохранённой NVS-конфигурации; отложить решение о подключении, затем разрешить | До разрешения приходит только `hello`; GPIO не назначаются. После разрешения появляется «Настроить», пустой heartbeat удерживает связь дольше 45 секунд |
| Предпросмотр и валидация | Добавить GPIO-выход на GPIO 4, затем попытаться назначить тот же пин второму компоненту или задать недопустимый диапазон | Ошибка видна у поля; неправильная конфигурация не заменяет сохранённую и не меняет работающие выходы |
| Цифровой выход | Настроить GPIO 4, `active_high=true`, начальное `false`; после подтверждения включить и выключить | На пине меняются HIGH/LOW, логическое состояние совпадает с карточкой. При `active_high=false` уровни меняются местами |
| Цифровой вход | Настроить свободный GPIO 7, подтяжку `up` и интервал 100 мс; переключать вход между допустимыми уровнями | Значение `true` соответствует HIGH, `false` — LOW; состояние обновляется. Название параметра не меняет эту полярность |
| ADC и единицы | Настроить GPIO 5, raw 200–3900, итоговый диапазон 0–1200, единицу `lx`; проверить несколько входных уровней | Карточка и Blockly используют целое значение и заданную единицу; вне raw-диапазона результат ограничен 0 или 1200. Реальные люксы требуют калибровки датчика |
| PWM | Настроить GPIO 6 с диапазоном 0–255; отправить 0, 128 и 255, затем несколько раз сменить PWM-пин на другие свободные поддерживаемые пины | Выход меняется по заполнению; повторная настройка не исчерпывает PWM-каналы. После смены PWM на цифровой выход этот GPIO управляется обычным переключателем |
| Поиск устройства | Выбрать фактический GPIO 38/48 встроенного NeoPixel либо отдельный свободный GPIO-индикатор; нажать значок поиска | Индикатор мигает пять раз, затем выключается. Команды другим выходам выполняются во время мигания; пин индикатора нельзя одновременно назначить компоненту |
| Повтор без сброса | Включить GPIO-выход, установить PWM выше начального значения; нажать «Повторить сохранённую» | Версия не увеличивается, значения выходов сохраняются. В Serial Monitor есть `Configuration is already active; GPIO and NVS unchanged.` |
| Сохранение offline | Отключить ESP32 от Gateway, изменить конфигурацию и сохранить, затем вернуть связь | Статус ожидания сохраняется; новая версия отправляется после подключения и становится подтверждённой только после ACK |
| Переподключение | Изменить выход командой, прервать Wi-Fi и восстановить его без перезапуска платы | Повторный `hello` не создаёт новую версию, текущий выход сохраняется; восстановленная связь продолжает передавать состояние |
| Перезапуск платы | Отключить и включить питание уже настроенной ESP32 | Конфигурация загружается из NVS, выходы принимают заданные начальные значения; повторная доставка Gateway не сбрасывает их повторно |
| Ошибка применения | В отдельном протокольном стенде отправить неверный хэш либо документ с конфликтом GPIO, в том числе с заголовком уже применённой версии | ESP32 возвращает `success=false`; версия и рабочие выходы не меняются. Обычный интерфейс блокирует такие документы ещё до отправки |
| Восстановление из ESP32 | Запустить Gateway с новой тестовой БД и разрешить подключение настроенной платы | Gateway запрашивает отчёт, проверяет конфигурацию, хэш и Schema, сохраняет их в БД и JSON; неправильный хэш не принимается |
| Автоматизация | После подтверждения выбрать реальные ID параметров в Blockly: изменение ADC → условие → установка GPIO-выхода | Используется принятая Schema, сценарий получает телеметрию и отправляет обычную подтверждаемую команду |
