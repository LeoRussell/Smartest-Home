# Длительная проверка стабильности

`gateway/soak_test.py` запускает настоящий Python Gateway с временной SQLite-базой,
виртуальным ESP32 и виртуальным браузером. Они обмениваются JSON через реальные
WebSocket-соединения на случайном локальном порту `127.0.0.1`. Рабочая база,
порты `8765`/`8080`, COM-порты и физические GPIO в этой проверке не используются.
Скрипт можно запускать одновременно с обычным Gateway.

## Быстрая проверка

Из корня проекта в PowerShell, после установки зависимостей из основного README:

```powershell
.\.venv\Scripts\python.exe -X utf8 gateway\soak_test.py --cycles 3 --interval 0 --report "$env:TEMP\gateway-soak.json"
```

Linux/macOS:

```sh
.venv/bin/python gateway/soak_test.py --cycles 3 --interval 0 --report /tmp/gateway-soak.json
```

Без `--report` создаётся новый JSON-файл во временном каталоге; его путь выводится
в конце. Существующий файл можно заменить, только если это уже отчёт этого
скрипта. Базы данных и чужие JSON-файлы он отказывается перезаписывать.

Каждый завершённый цикл проверяет:

- подключение заранее разрешённого тестового устройства, приём Schema и состояния;
- ручную команду, подтверждение и запись результата в SQLite;
- повторный ACK без повторного завершения команды;
- потерю первого ACK, повторную доставку с тем же ID и возврат сохранённого результата
  без повторного действия; устаревший результат не должен заменять свежую телеметрию;
- удаление результата из ограниченного кэша после потери ACK: повтор с
  `require_cached_result: true` завершается ошибкой без повторного действия;
- завершение сценария с ошибкой, если устройство не подтверждает команду;
- повторное подключение браузера и получение актуального списка устройств;
- сохранение незавершённой ручной команды при разрыве связи или перезапуске Gateway,
  возврат сохранённого результата после подключения и остановку прерванного сценария;
- освобождение соединений и задач при остановке.

Новые команды отключённому устройству здесь не ставятся: проверяется восстановление
ручной команды, которая уже была выполнена до разрыва, но её ACK не дошёл до Gateway.
Если её результат больше не доступен в кэше, повтор запрещён: Gateway сообщает об ошибке,
а не выполняет действие позже. Виртуальное устройство объявляет оба флага
`command_dedup` и `command_replay_guard`.
Устройство заранее разрешено только внутри временной базы; диалог ручного допуска проверяется
другими тестами. Сохранённый результат имитируется в памяти виртуального ESP32:
проверка настоящей flash-памяти платы относится к испытанию прошивки.

## Длительный запуск

Для трёхминутной проверки:

```powershell
.\.venv\Scripts\python.exe -X utf8 gateway\soak_test.py --duration 180 --interval 0.25 --report "$env:TEMP\gateway-soak-3min.json"
```

Для суток с перезапуском Gateway каждые 100 циклов:

```powershell
.\.venv\Scripts\python.exe -X utf8 gateway\soak_test.py --duration 86400 --interval 5 --restart-every 100 --report "$env:TEMP\gateway-soak-24h.json"
```

Для проверки непрерывной работы одного экземпляра Gateway с периодическими
разрывами соединения виртуального устройства:

```powershell
.\.venv\Scripts\python.exe -X utf8 gateway\soak_test.py --duration 86400 --interval 5 --restart-every 0 --report "$env:TEMP\gateway-soak-uptime.json"
```

В Linux/macOS замените путь к Python и путь отчёта, как в быстром примере.
Без указания `--restart-every` Gateway перезапускается после каждого цикла.
`--cycles` и `--duration` нельзя задавать вместе; без обоих выполняется 10 циклов.
Текущий цикл доводится до конца, поэтому итоговое время может немного превышать
`--duration`. Даже при очень короткой длительности выполняется один полный цикл.

Таймер подтверждения ускорен до `0.08` секунды: это проверка логики доставки,
а не измерение задержек Wi-Fi. Его можно изменить, например `--command-timeout 5`;
тогда этапы намеренной потери ACK и таймаута будут занимать дольше.

Ограничения аргументов проверяются до создания стенда: `--cycles` — целое число
от 1, `--duration` — положительное конечное число секунд, `--interval` — конечное
число от 0. `--command-timeout` допускает 0,01–30 секунд, `--restart-every` —
целое число от 0. Эти параметры меняют только виртуальный стенд, а не настройки
работающего Gateway или ESP32.

Отчёт записывается атомарно при запуске, после первого цикла, затем примерно каждые
30 секунд на границе завершённого цикла и при выходе. Он содержит длительность,
счётчики проверок, размер временной базы, последние 80 строк журнала и ошибки с
номером цикла и этапом. История виртуальных команд остаётся во временной базе
до завершения процесса, поэтому при длительном прогоне её размер растёт.
Списки сетевых сообщений и диагностический журнал в памяти ограничены.

Статус `running` означает, что отчёт промежуточный; `passed` — все выполненные
циклы прошли; `failed` — обнаружена ошибка; `interrupted` — запуск остановлен.
Коды завершения: `0` — успех, `1` — ошибка, `130` — прерывание через Ctrl+C.
При штатном завершении и Ctrl+C временная база удаляется, итоговый JSON остаётся.
При принудительном завершении процесса последний отчёт может остаться `running`,
а временные файлы — не удалиться.
Окно терминала и компьютер должны работать весь срок испытания.

## Автоматические проверки в CI

В GitHub Actions короткий запуск `--cycles 3 --interval 0` выполняется на Ubuntu
и Windows после серверных и браузерных тестов. Если предыдущий этап завершился
ошибкой, soak-тест этой задачи не запускается. Его успешный результат относится
к трём завершённым циклам виртуального стенда, а не к суточной работе платы.
Проверки реальной ESP32 выполняются отдельно.

## Отдельная проверка настоящей ESP32

Программный отчёт всегда содержит `scope: "software_loopback"` и
`physical_device_tested: false`. Он не подтверждает стабильность питания, Wi-Fi,
GPIO, драйвера LED или flash-памяти реальной платы и не означает, что суточный
прогон уже выполнен.

Для физического испытания используйте обычный запуск из [README](../README.md),
нужную прошивку из [esp32/README.md](../esp32/README.md) и настройки своей платы.
Для тестовой платы с LED на GPIO48 проверьте соответствие типа индикатора
реальному подключению: обычный GPIO и адресный RGB-индикатор требуют разных драйверов.
Настройка описана в [универсальной прошивке](UNIVERSAL_FIRMWARE.md) и
[пользовательской прошивке](ADVANCED_FIRMWARE.md).

Перед длительным прогоном вручную проверьте управление LED, «Найти устройство»
и сценарий выключения через пять секунд, включая повторное включение с новым
отсчётом. Затем отдельно проверьте краткую потерю Wi-Fi и перезапуск Gateway:
незавершённая ручная команда должна восстановиться согласно возможностям прошивки,
а прерванный запуск сценария не должен продолжиться сам.

Оставьте обычный Gateway и плату на 24–48 часов. В конце сохраните время начала и
окончания, версии кода, число неожиданных отключений, их причины, Wi-Fi и время
работы платы из [истории соединений](CONNECTIONS.md). Разделяйте запланированные
разрывы и самопроизвольные; падение uptime платы помогает отличить перезагрузку
от одного лишь переподключения. Это отдельный результат испытания, а не часть
JSON-отчёта виртуального стенда.
