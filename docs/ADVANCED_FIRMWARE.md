# Пользовательская прошивка ESP32

Пользовательская прошивка отвечает за датчики, исполнительные механизмы и
собственные алгоритмы устройства. `GatewayClient` берёт на себя подключение к
Wi-Fi и WebSocket Gateway; Schema и смысл команд задаёт прошивка.

Если достаточно цифровых входов/выходов, ADC и PWM без C++, начните с
[универсальной прошивки](UNIVERSAL_FIRMWARE.md). Это руководство — для своих
датчиков, драйверов, действий и автономных режимов.

## Создание своего проекта на основе примера

Все пути и команды ниже считаются от корня репозитория.

1. Скопируйте `esp32/examples/led` в `esp32/examples/my-device`. При таком
   расположении пути к `../../shared/lib` и `../../shared/include` останутся
   рабочими. Скопированные `.pio/` не являются исходниками и для нового
   проекта не нужны.
2. В `include/device_config.h` задайте уникальный `DEVICE_ID`, имя и модель.
   Для совместимости со всеми операциями интерфейса используйте ID длиной
   1–64 символа: латинская буква, затем буквы, цифры, `_` или `-`.
3. Выберите плату и драйвер в `platformio.ini`; укажите свою сеть и адрес
   Gateway в общем `esp32/shared/include/secrets.h`.
4. В `src/DeviceSchema.cpp` объявите реальные параметры, действия и
   возможности. В `main.cpp` реализуйте чтение датчиков, управление выходами,
   подтверждение команд и отправку состояния. Одного объявления в Schema
   недостаточно, чтобы GPIO начал работать.
5. При необходимости добавьте авторские режимы в `DeviceModes.cpp`.
   Оставьте пустой реестр, если режимов нет. При смене Schema увеличьте её
   версию в `sendHello()`; отдельно обновляйте версию самой прошивки.
6. Соберите, загрузите и разрешите подключение в Gateway:

   ```powershell
   pio run -d esp32/examples/my-device -e esp32-s3-devkitc-1
   pio run -d esp32/examples/my-device -e esp32-s3-devkitc-1 -t upload
   pio device monitor -d esp32/examples/my-device -e esp32-s3-devkitc-1
   ```

Сначала проверьте показания и ручные команды, затем используйте их в
[Blockly](AUTOMATION.md). У каждой физической платы должен быть свой ID:
одинаковые ID приводят к замене соединения первой платы второй.

## Подключение библиотеки

Рабочий пример пользовательской прошивки расположен в `esp32/examples/led`;
его `platformio.ini` использует общую библиотеку из `esp32/shared/lib/GatewayClient`.
Для другого проекта скопируйте каталог `GatewayClient` в его каталог `lib`.
Библиотека объявляет зависимости WebSockets и ArduinoJson в `library.json`.

При переносе за пределы репозитория скопируйте также `secrets.h` в доступный
каталог `include/` и измените `lib_dir`/пути включения в `platformio.ini`.
Отдельно выберите свою плату: `GatewayClient` рассчитан на ESP32 с Arduino.

В рабочем профиле код разделён по ответственности:

- `esp32/shared/lib/GatewayClient` — общие Wi-Fi, WebSocket, переподключение и JSON-транспорт;
- `esp32/examples/led/src/main.cpp` — запуск, телеметрия и обработчики команд конкретного
  устройства;
- `esp32/examples/led/src/DeviceSchema.cpp` — описание параметров и возможностей;
- `esp32/examples/led/src/DeviceModes.cpp` — реестр режимов и их обработчики;
- `esp32/examples/led/include/device_config.h` — ID и настройки устройства;
- `esp32/examples/led/platformio.ini` — профили платы, драйвера и GPIO;
- `esp32/shared/include/secrets.h` — общие для прошивок настройки Wi-Fi и Gateway.

В собственном проекте можно сохранить такое же разделение или объединить
файлы, если проект небольшой. Не добавляйте Wi-Fi-пароль в публикуемые файлы.

Создайте локальный `esp32/shared/include/secrets.h` с параметрами сети:

```cpp
#pragma once
#define WIFI_SSID "имя Wi-Fi"
#define WIFI_PASSWORD "пароль Wi-Fi"
#define GATEWAY_IP "192.168.0.102"
```

По умолчанию рабочий пример регистрирует устройство `esp32-01`, объявляет
управляемый параметр `led`, принимает команды и отправляет подтверждения.
Он рассчитан на ESP32-S3 с обычным LED на GPIO 48. Скопируйте
`esp32/shared/include/secrets.example.h` в `esp32/shared/include/secrets.h`, укажите Wi-Fi,
затем соберите пример:

```powershell
pio run -d esp32/examples/led
```

Чтобы прошить плату, добавьте `-t upload`. Для другой платы выберите профиль
через `-e` или настройте пин и драйвер под её схему. Профиль по умолчанию
демонстрирует обычный GPIO LED; для адресного RGB-индикатора доступны
NeoPixel-профили в `esp32/examples/led/platformio.ini`.

В собственном обработчике `WStype_CONNECTED` отправляйте `hello`. Например,
светочувствительный датчик может объявить числовой параметр `illuminance` с
доступом `read_only` и единицей `lx`. Затем прошивка отправляет `state` с
текущим `data.parameters.illuminance`; Gateway проверяет Schema и показывает
значение в устройстве и блоках автоматизации.

## Жизненный цикл соединения

Используйте один экземпляр `GatewayClient`. В `setup()` вызовите
`gateway.begin(GATEWAY_IP, GATEWAY_PORT, WIFI_SSID, WIFI_PASSWORD, handler)`,
а в каждом проходе `loop()` — `gateway.loop()`. Аргумент `handler` имеет
сигнатуру `void handler(WStype_t type, uint8_t* payload, size_t length)`.
`sendJson(JsonDocument&)` и `sendText(const String&)` отправляют данные по
этому соединению. `isConnected()` проверяет транспорт, но не разрешение
Gateway.

Порядок сообщений:

1. При `WStype_CONNECTED` сбросьте свой флаг регистрации и отправьте один
   `hello` с актуальной Schema. Повторяйте это после каждого переподключения.
2. Дождитесь `hello_ack`: запрос доступа может ждать решения пользователя
   до 180 секунд. До ACK не отправляйте состояние и не исполняйте команды.
3. При ACK установите флаг регистрации и сразу передайте полный `state`.
   После этого отправляйте изменения и периодический полный отчёт, например
   раз в 10 секунд, включая неизменившиеся показания.
4. При `WStype_DISCONNECTED` сбросьте регистрацию. Wi-Fi и WebSocket
   восстанавливает общая библиотека; не добавляйте конкурирующий таймер
   `WiFi.reconnect()`.

Не блокируйте `loop()` длинным `delay()`, ожиданием кнопки или циклом режима.
Используйте `millis()` и короткие шаги: библиотеке нужно регулярно
обрабатывать команды и отвечать на серверные Ping. Длительная операция может
запускаться действием, а её прогресс/результат — передаваться параметрами
состояния. Таймаут ожидания результата команды в Gateway — 5 секунд.

Входящий JSON разбирайте с учётом длины:
`deserializeJson(document, payload, length)`. Буфер callback не следует
считать строкой с гарантированным завершающим нулём. Проверяйте типы,
допустимые значения и ID операций также в самой прошивке.

## Формат сообщений

Регистрация устройства — сообщение `hello` с уникальным ID и Schema:

```json
{
  "type": "hello",
  "device": "esp32-lab-sensor",
  "name": "Датчик в мастерской",
  "protocol_version": 2,
  "firmware_version": "1.0.0",
  "schema_version": 1,
  "command_dedup": false,
  "schema": {
    "format_version": 1,
    "parameters": {
      "illuminance": {
        "label": "Освещённость",
        "type": "number",
        "access": "read_only",
        "unit": "lx"
      },
      "relay": {
        "label": "Реле",
        "type": "boolean",
        "access": "read_write",
        "control": "toggle"
      }
    },
    "actions": {}
  }
}
```

Идентификатор `device` задаётся латиницей и должен быть уникальным. `name` —
отображаемое пользователю имя и может быть русским. Увеличивайте
`schema_version`, когда меняется объявленная Schema. Gateway всё равно
сравнивает содержимое Schema, а не полагается только на номер версии.

Ответ после разрешения подключения, например:

```json
{
  "type": "hello_ack",
  "device": "esp32-lab-sensor",
  "schema_status": "saved"
}
```

Статус `saved` означает сохранённую Schema, `preserved` — сохранение ранее
принятой Schema при подключении старого клиента без неё.
Статус `pending` означает, что предложенная Schema ожидает решения: команды
Gateway временно заблокированы. `hello_ack` всё равно подтверждает допуск
соединения. После переименования `device` в ACK может быть ID Gateway;
исходный ID прошивки менять по этому ответу не нужно. В своих `state` и
`command_result` продолжайте передавать тот же `device`, что в `hello`.
Gateway сопоставляет его с переименованным ID. Входящие команды также
адресуются исходному ID прошивки.

### Состояние и heartbeat

```json
{
  "type": "state",
  "id": 1,
  "device": "esp32-lab-sensor",
  "data": {
    "parameters": {"illuminance": 124.5, "relay": false}
  }
}
```

Каждое значение должно соответствовать принятой Schema. `state` может
содержать часть параметров; остальные значения не сбрасываются, но и не
становятся свежее. Gateway использует показание в сценариях до 45 секунд
после его принятия в текущей сессии. Пустой объект `parameters` подтверждает
прикладную активность, но не обновляет показания.

`id` состояния может быть счётчиком для удобства диагностики; он не заменяет
`command_id`. Новое числовое значение должно быть JSON-числом, а boolean —
`true`/`false`, без кавычек. `unit` передаётся в Schema, а не приписывается к
значению: отправляйте `124.5`, а не `"124.5 lx"`.

### Установка параметра

Gateway отправляет команду параметра так:

```json
{
  "type": "command",
  "id": "cmd-example",
  "device": "esp32-lab-sensor",
  "data": {
    "command": "set",
    "command_id": "cmd-example",
    "parameter": "relay",
    "value": true
  }
}
```

После фактического выполнения прошивка отвечает `command_result`, указав то
же значение, которое удалось применить:

```json
{
  "type": "command_result",
  "id": "cmd-example",
  "command_id": "cmd-example",
  "device": "esp32-lab-sensor",
  "success": true,
  "data": {"parameter": "relay", "value": true}
}
```

Для произвольной операции используйте `data.command: "invoke"`, ID действия
из `schema.actions` и объект `data.arguments`. В ответе укажите ID действия в
`data.action`. Командный обработчик текущей прошивки в
`esp32/examples/led/src/main.cpp` — рабочий пример приёма `set` и `invoke`, передачи
результата и защиты от повторного выполнения через `command_id`.

### Действия и ошибки

Действие сначала объявляется в `schema.actions`. Например, для
`"calibrate": {"label": "Калибровка", "arguments": {"offset": {"type": "number", "min": -5, "max": 5}}}`
команда будет такой:

```json
{
  "type": "command",
  "id": "cmd-calibrate",
  "device": "esp32-lab-sensor",
  "data": {
    "command": "invoke",
    "command_id": "cmd-calibrate",
    "action": "calibrate",
    "arguments": {"offset": 0.5}
  }
}
```

Успешный ответ содержит тот же `command_id`, `success: true` и
`data: {"action": "calibrate"}`. При ошибке отправьте `success: false` и текст
в **`data.error`**:

```json
{
  "type": "command_result",
  "id": "cmd-calibrate",
  "command_id": "cmd-calibrate",
  "device": "esp32-lab-sensor",
  "success": false,
  "data": {"action": "calibrate", "error": "Sensor is not ready"}
}
```

Для отказа `set` вместо `data.action` передайте `data.parameter` и фактическое
`data.value`, если оно известно. Положительное подтверждение параметра должно
содержать запрошенное и реально установленное значение. Несовпадающее
значение или неверный тип Gateway считает ошибкой. Отчёт `state` не заменяет
`command_result`; для завершения ожидающей команды нужен её ответ.

## Подтверждения и повторная доставка

Флаг `command_dedup` должен быть `true` только если прошивка действительно
сохраняет и повторно использует результат для каждого ID команды. Без этой
защиты Gateway не повторяет команду после потери подтверждения, чтобы не
запустить действие дважды. LED-пример хранит последние 16 результатов в
NVS; библиотека `GatewayClient` намеренно не подменяет эту логику.

Для повторного `command_id` отправляйте сохранённый результат, не запускайте
действие заново. Хранение только в RAM не защищает от повторов после
перезапуска платы. Даже NVS-кэш не даёт абсолютной гарантии «ровно один раз»:
сбой питания между выполнением действия и сохранением результата оставляет
неопределённость. Без реализованного кэша объявляйте `command_dedup: false`,
как текущая универсальная прошивка.

## Добавление собственного датчика

Например, в скопированном LED-проекте можно добавить сырой ADC-вход на GPIO 4.
В `buildDeviceSchema()` после создания объекта `parameters`:

```cpp
JsonObject sensor = parameters["light_raw"].to<JsonObject>();
sensor["label"] = "Аналоговый вход";
sensor["type"] = "integer";
sensor["access"] = "read_only";
sensor["unit"] = "raw";
sensor["min"] = 0;
sensor["max"] = 4095;
```

В `setup()` задайте `pinMode(4, INPUT)` и `analogReadResolution(12)`.
В `sendState()` после создания `parameters` добавьте:

```cpp
parameters["light_raw"] = analogRead(4);
```

Увеличьте `schema_version` в `sendHello()`, загрузите изменённую прошивку и
примите новую Schema. Вход появится в карточке и Blockly. Обработчик `set`
для него не нужен, поскольку параметр только для чтения. Выберите GPIO по
распиновке своей платы; `raw` — отсчёты ADC, а не люксы. Для физических единиц
нужны формула и калибровка: тогда меняются и значение, и `unit`/диапазон Schema.

При добавлении управляемого параметра также расширьте обработчик `set`.
При добавлении действия расширьте `invoke`. При изменении состояния своим
алгоритмом отправляйте `state`, даже если команда от Gateway не приходила.

## Режимы устройства

Сложные режимы остаются в пользовательской прошивке. Зарегистрируйте их в
`esp32/examples/led/src/DeviceModes.cpp`: общий код добавит операции режима в Schema и
направит команды соответствующим обработчикам. Допустимые операции
`select`, `enable` и `disable` ссылаются на ID этих действий. При необходимости
режим может ссылаться на параметр состояния и перечислить конфликтующие
режимы. Gateway проверит ссылки и отобразит доступные операции в карточке
устройства и автоматизациях. Подробный пример структуры реестра обработчиков
приведён в [`AUTOMATION.md`](AUTOMATION.md#действия-и-прошивочные-режимы).

Флаги `MODE_CAN_SELECT`, `MODE_CAN_ENABLE`, `MODE_CAN_DISABLE` описывают
операции реестра прошивки. Они превращаются в `schema.modes.operations`,
которые ссылаются на реальные действия из `schema.actions`. Gateway
вызывает эти действия, а алгоритм исполняется на ESP32. Необязательные
`status_parameter`/`status_value` связывают режим с обычным параметром
состояния; произвольные внутренние переменные Gateway сам не читает.

В реестре до восьми режимов. Оставляйте завершающую пустую запись; для
статуса используйте обработчик `isActive`. Вызовы выполняйте быстро,
а длительное поведение обновляйте в `loop()`. Работа режима, реализованного
на ESP32, может продолжаться без Gateway; серверному сценарию нужен
работающий Gateway и связь с используемыми устройствами.

## Обновление Schema и проверка прошивки

Для обычной прошивки достаточно передавать актуальную Schema в каждом
`hello`. Gateway сравнивает её по содержимому и повторно предлагает изменения
при следующем подключении, если пользователь оставил прежнюю версию.
Сообщение `schema_update` поддерживается для смены Schema без переподключения,
но не является обязательной частью обычного запуска.

Проверьте после изменения: первый допуск и повторное подключение, полный
`state` после ACK, типы и единицы, ручную команду и её отказ, повтор
`command_id` при включённом dedup, сценарий с паузой и восстановление связи.
Входящая Schema ограничена 60 КиБ, всё WebSocket-сообщение — 64 КиБ.
Численные ограничения параметров и действий перечислены в
[справочнике Schema](DEVICE_SCHEMA.md).

Физический индикатор не обязателен. Объявляйте `capabilities.identify` и
`actions.identify` только при наличии реализованного способа поиска устройства;
метаданные сами по себе светодиод не включат. Диагностика общих Wi-Fi и
WebSocket-логов описана в
[руководстве универсального профиля](UNIVERSAL_FIRMWARE.md#связь-и-диагностика-переподключений).

## Выбор профиля и границы реализации

`GatewayClient` переиспользуется пользовательской прошивкой и переносит
Wi-Fi, WebSocket, повторное подключение и отправку JSON в отдельную библиотеку.
Пользовательская прошивка сама объявляет Schema и реализует действия и режимы.
Для обычной настройки GPIO без собственного кода есть отдельный проект
[`esp32/universal`](../esp32/universal) и руководство
[`UNIVERSAL_FIRMWARE.md`](UNIVERSAL_FIRMWARE.md). Он поддерживает ограниченный
реестр драйверов, принимает аппаратную конфигурацию, проверяет её, сохраняет
в NVS и отправляет подтверждение с актуальной Schema. Новые типы датчиков
нельзя включить одной записью в веб-конструкторе: необходимо реализовать
драйвер в прошивке и соответствующую серверную проверку.
