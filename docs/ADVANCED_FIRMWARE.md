# Пользовательская прошивка ESP32

Пользовательская прошивка отвечает за датчики, исполнительные механизмы и
собственные алгоритмы устройства. `GatewayClient` берёт на себя подключение к
Wi-Fi и WebSocket Gateway; Schema и смысл команд задаёт прошивка.

Если достаточно цифровых входов/выходов, ADC, PWM и DS18B20 без C++, начните с
[универсальной прошивки](UNIVERSAL_FIRMWARE.md). Это руководство — для своих
датчиков, драйверов, действий и автономных режимов.

## Что именно писать в собственной прошивке

Для своего устройства нужны три части:

1. **Описание интерфейса — Schema.** Какие показания, команды и режимы
   доступны, как они называются, в каких единицах и с какими ограничениями.
2. **Работа с оборудованием.** Чтение датчика, установка GPIO, работа дисплея
   и алгоритм выбранного режима. Этот код исполняется на самой ESP32.
3. **Обмен с Gateway.** Регистрация, состояние и ответы на команды. В копии
   LED-примера эта часть уже написана и использует общий `GatewayClient`.

| Что объявить | Когда использовать | Пример |
| --- | --- | --- |
| `parameters`, `read_only` | Показание или состояние, которое можно прочитать | Температура `19.25`, единица `°C`; признак `blink_active` |
| `parameters`, `read_write` | Значение, которое можно установить | `led: true`, скорость вентилятора `40` |
| `actions` | Отдельная операция | Найти устройство, откалибровать датчик |
| `modes` | Готовый алгоритм длительной работы | Ручное управление, мигание, ночной режим дисплея |
| `capabilities` | Дополнительный объявленный признак | У устройства реализовано действие поиска `identify` |

Надпись **«Режимы не объявлены прошивкой»** означает, что в принятой Schema
нет `modes`. Gateway не придумывает режимы по наличию LED или датчика.
Универсальная прошивка с DS18B20 предоставляет измерение температуры и сама
по себе не объявляет авторские режимы. В LED-примере режимы объявляются
кодом; для своих алгоритмов измените его и снова загрузите прошивку.

Описание в Schema и обработчик дополняют друг друга. Запись `"blink"` в JSON
не заставляет лампу мигать: обработчик выбирает режим, а короткие шаги
алгоритма выполняются из `loop()`. Режим ESP32 может работать при закрытом
браузере и без соединения с Gateway. Сам Gateway не компилирует C++ из Schema.

## Создание своего проекта на основе примера

Все пути и команды ниже считаются от корня репозитория.

1. Скопируйте `esp32/examples/led` в `esp32/examples/my-device`. При таком
   расположении пути к `../../shared/lib` и `../../shared/include` останутся
   рабочими. Перенесите `platformio.ini`, `include/` и `src/`, а `.pio/`
   оставьте в исходном проекте: это результаты сборки и скачанные библиотеки.
2. В `include/device_config.h` задайте уникальный `DEVICE_ID`, имя и модель.
   Для совместимости со всеми операциями интерфейса используйте ID длиной
   1–64 символа: латинская буква, затем буквы, цифры, `_` или `-`.
3. Выберите плату и драйвер в `platformio.ini`; укажите свою сеть и адрес
   Gateway в общем `esp32/shared/include/secrets.h`.
4. В `src/DeviceSchema.cpp` объявите реальные параметры, действия и
   возможности. В `main.cpp` реализуйте чтение датчиков, управление выходами,
   подтверждение команд и отправку состояния. Одного объявления в Schema
   недостаточно, чтобы GPIO начал работать.
5. При необходимости добавьте авторские режимы в `DeviceModes.cpp`.
   Оставьте пустой реестр, если режимов нет. При смене Schema увеличьте её
   версию в `sendHello()`; отдельно обновляйте версию самой прошивки.
6. Соберите, загрузите и разрешите подключение в Gateway:

   ```powershell
   pio run -d esp32/examples/my-device -e esp32-s3-devkitc-1
   pio run -d esp32/examples/my-device -e esp32-s3-devkitc-1 -t upload
   pio device monitor -d esp32/examples/my-device -e esp32-s3-devkitc-1
   ```

Сначала проверьте показания и ручные команды, затем используйте их в
[Blockly](AUTOMATION.md). У каждой физической платы должен быть свой ID:
одинаковые ID приводят к замене соединения первой платы второй.

## Подключение библиотеки

Рабочий пример пользовательской прошивки расположен в `esp32/examples/led`;
его `platformio.ini` использует общую библиотеку из `esp32/shared/lib/GatewayClient`.
Для другого проекта скопируйте каталог `GatewayClient` в его каталог `lib`.
Библиотека объявляет зависимости WebSockets и ArduinoJson в `library.json`.

При переносе за пределы репозитория скопируйте также `secrets.h` в доступный
каталог `include/` и измените `lib_dir`/пути включения в `platformio.ini`.
Отдельно выберите свою плату: `GatewayClient` рассчитан на ESP32 с Arduino.

В рабочем профиле код разделён по ответственности:

- `esp32/shared/lib/GatewayClient` — общие Wi-Fi, WebSocket, переподключение, JSON-транспорт и NVS-кэш команд;
- `esp32/examples/led/src/main.cpp` — запуск, телеметрия и обработчики команд конкретного
  устройства;
- `esp32/examples/led/src/DeviceSchema.cpp` — описание параметров и возможностей;
- `esp32/examples/led/src/DeviceModes.cpp` — реестр режимов и их обработчики;
- `esp32/examples/led/src/LedModes.h/.cpp` — алгоритмы ручного режима и мигания,
  состояние выбранного режима и короткий шаг обновления;
- `esp32/examples/led/include/device_config.h` — ID и настройки устройства;
- `esp32/examples/led/platformio.ini` — профили платы, драйвера и GPIO;
- `esp32/shared/include/secrets.h` — общие для прошивок настройки Wi-Fi и Gateway.

В собственном проекте можно сохранить такое же разделение или объединить
файлы, если проект небольшой. Не добавляйте Wi-Fi-пароль в публикуемые файлы.

Создайте локальный `esp32/shared/include/secrets.h` с параметрами сети:

```cpp
#pragma once
#define WIFI_SSID "имя Wi-Fi"
#define WIFI_PASSWORD "пароль Wi-Fi"
#define GATEWAY_IP "192.168.0.104"
```

IP здесь — пример текущего компьютера в LAN. Возьмите актуальный адрес из
вывода `py run.py`; `localhost` и `0.0.0.0` не являются адресом компьютера
для ESP32. Если DHCP изменил IP, обновите сетевую настройку и прошивку.

По умолчанию рабочий пример регистрирует устройство `esp32-01`, объявляет
управляемый параметр `led`, принимает команды и отправляет подтверждения.
Он рассчитан на ESP32-S3 с обычным LED на GPIO 48. Скопируйте
`esp32/shared/include/secrets.example.h` в `esp32/shared/include/secrets.h`, укажите Wi-Fi,
затем соберите пример:

```powershell
pio run -d esp32/examples/led
```

Если обычный PowerShell не знает `pio`, у установки PlatformIO из VS Code
можно вызвать CLI полным путём:

```powershell
& "$env:USERPROFILE\.platformio\penv\Scripts\pio.exe" run -d esp32/examples/my-device -e esp32-s3-devkitc-1
```

Чтобы прошить плату, добавьте `-t upload`. Для другой платы выберите профиль
через `-e` или настройте пин и драйвер под её схему. Профиль по умолчанию
демонстрирует обычный GPIO LED; для адресного RGB-индикатора доступны
NeoPixel-профили в `esp32/examples/led/platformio.ini`.

В собственном обработчике `WStype_CONNECTED` отправляйте `hello`. Например,
светочувствительный датчик может объявить числовой параметр `illuminance` с
доступом `read_only` и единицей `lx`. Затем прошивка отправляет `state` с
текущим `data.parameters.illuminance`; Gateway проверяет Schema и показывает
значение в устройстве и блоках автоматизации.

## Жизненный цикл соединения

Используйте один экземпляр `GatewayClient`. В `setup()` вызовите
`gateway.begin(GATEWAY_IP, GATEWAY_PORT, WIFI_SSID, WIFI_PASSWORD, handler)`,
а в каждом проходе `loop()` — `gateway.loop()`. Аргумент `handler` имеет
сигнатуру `void handler(WStype_t type, uint8_t* payload, size_t length)`.
`sendJson(JsonDocument&)` и `sendText(const String&)` отправляют данные по
этому соединению. `isConnected()` проверяет транспорт, но не разрешение
Gateway.

Порядок сообщений:

1. При `WStype_CONNECTED` сбросьте свой флаг регистрации и отправьте один
   `hello` с актуальной Schema. Повторяйте это после каждого переподключения.
2. Дождитесь `hello_ack`: запрос доступа может ждать решения пользователя
   до 180 секунд. До ACK не отправляйте состояние и не исполняйте команды.
3. При ACK установите флаг регистрации и передайте доступное текущее состояние.
   Для датчика с асинхронным чтением сначала дождитесь новой конверсии.
   После этого отправляйте изменения и периодический отчёт, например раз в
   10 секунд. Неизменившийся результат нового измерения тоже можно отправить;
   повтор старого кэша не заменяет новое измерение датчика.
4. При `WStype_DISCONNECTED` сбросьте регистрацию. Wi-Fi и WebSocket
   восстанавливает общая библиотека; не добавляйте конкурирующий таймер
   `WiFi.reconnect()`.

Не блокируйте `loop()` длинным `delay()`, ожиданием кнопки или циклом режима.
Используйте `millis()` и короткие шаги: библиотеке нужно регулярно
обрабатывать команды и отвечать на серверные Ping. Длительная операция может
запускаться действием, а её прогресс/результат — передаваться параметрами
состояния. Таймаут ожидания результата команды в Gateway — 5 секунд.

Входящий JSON разбирайте с учётом длины:
`deserializeJson(document, payload, length)`. Буфер callback не следует
считать строкой с гарантированным завершающим нулём. Проверяйте типы,
допустимые значения и ID операций также в самой прошивке.

## Формат сообщений

Регистрация устройства — сообщение `hello` с уникальным ID и Schema:

```json
{
  "type": "hello",
  "device": "esp32-lab-sensor",
  "name": "Датчик в мастерской",
  "protocol_version": 2,
  "firmware_version": "1.0.0",
  "schema_version": 1,
  "command_dedup": false,
  "schema": {
    "format_version": 1,
    "parameters": {
      "illuminance": {
        "label": "Освещённость",
        "type": "number",
        "access": "read_only",
        "unit": "lx"
      },
      "relay": {
        "label": "Реле",
        "type": "boolean",
        "access": "read_write",
        "control": "toggle"
      }
    },
    "actions": {}
  }
}
```

Идентификатор `device` задаётся латиницей и должен быть уникальным. `name` —
отображаемое пользователю имя и может быть русским. Увеличивайте
`schema_version`, когда меняется объявленная Schema. Gateway всё равно
сравнивает содержимое Schema, а не полагается только на номер версии.

Ответ после разрешения подключения, например:

```json
{
  "type": "hello_ack",
  "device": "esp32-lab-sensor",
  "schema_status": "saved"
}
```

Статус `saved` означает сохранённую Schema, `preserved` — сохранение ранее
принятой Schema при подключении старого клиента без неё.
Статус `pending` означает, что предложенная Schema ожидает решения: команды
Gateway временно заблокированы. `hello_ack` всё равно подтверждает допуск
соединения. После переименования `device` в ACK может быть ID Gateway;
исходный ID прошивки менять по этому ответу не нужно. В своих `state` и
`command_result` продолжайте передавать тот же `device`, что в `hello`.
Gateway сопоставляет его с переименованным ID. Входящие команды также
адресуются исходному ID прошивки.

Оба примера проверяют адрес команды до выполнения и поиска в кэше:
`gateway.targetsDevice(document["device"], DEVICE_ID)` принимает исходный ID
прошивки и ID, полученный в `hello_ack`. Для этого обработчик ACK вызывает
`gateway.setGatewayDeviceId(document["device"])`. Сопоставление действует
только в текущем подключении и очищается при разрыве. Явный чужой ID,
пустая строка или неверный тип не запускают команду. Для старых сообщений
Gateway оставлена совместимость с отсутствующим полем `device` после
разрешения подключения; новый код всегда должен указывать адрес.

### Состояние и heartbeat

Общий `GatewayClient` добавляет в `hello` и `state` отдельный объект `health`:

```json
{
  "wifi_rssi": -62,
  "uptime_seconds": 1234,
  "reset_reason": "power_on",
  "last_disconnect_reason": null
}
```

Это верхнее поле сообщения, рядом с `type`, `device` и `data`, а не
`data.parameters`. При своём коде отправки вызовите
`gateway.appendHealth(document["health"].to<JsonObject>())`.
`uptime_seconds` — время ESP32 с момента загрузки, не длительность сессии
Gateway. Wi-Fi RSSI измеряется в dBm. Причина разрыва может содержать код
Wi-Fi; сервер дополнительно сохраняет закрытие WebSocket. Старые прошивки
без `health` продолжают работать, но не дают RSSI/время работы в карточке.

```json
{
  "type": "state",
  "id": 1,
  "device": "esp32-lab-sensor",
  "data": {
    "parameters": {"illuminance": 124.5, "relay": false}
  }
}
```

Каждое значение должно соответствовать принятой Schema. `state` может
содержать часть параметров; остальные значения не сбрасываются, но и не
становятся свежее. Gateway использует показание в сценариях до 45 секунд
после его принятия в текущей сессии. Пустой объект `parameters` подтверждает
прикладную активность, но не обновляет показания.

У датчика отправляйте результат действительно завершённого измерения.
При ошибке чтения пропустите параметр, а не подставляйте 0, `NaN` или прежнее
измерение с новым временем. После переподключения сделайте новое измерение:
данные из прошлой сессии не должны становиться «свежими». Возраст параметров
Gateway рассчитывает сам и передаёт интерфейсу; прошивка не формирует
`parameter_ages_seconds`.

В ArduinoJson записывайте значение через proxy объекта:

```cpp
JsonObject parameters = doc["data"]["parameters"].to<JsonObject>();
parameters["temperature"].set(temperatureC);
```

Чтение отсутствующего поля в изменяемый `JsonVariant` не создаёт слот для
последующей записи. Если нужен отдельный изменяемый вариант, сначала
создайте его через `.to<JsonVariant>()`, как в обработчиках рабочего примера.

`id` состояния может быть счётчиком для удобства диагностики; он не заменяет
`command_id`. Новое числовое значение должно быть JSON-числом, а boolean —
`true`/`false`, без кавычек. `unit` передаётся в Schema, а не приписывается к
значению: отправляйте `124.5`, а не `"124.5 lx"`.

### Установка параметра

Gateway отправляет команду параметра так:

```json
{
  "type": "command",
  "id": "cmd-example",
  "device": "esp32-lab-sensor",
  "data": {
    "command": "set",
    "command_id": "cmd-example",
    "parameter": "relay",
    "value": true
  }
}
```

После фактического выполнения прошивка отвечает `command_result`, указав то
же значение, которое удалось применить:

```json
{
  "type": "command_result",
  "id": "cmd-example",
  "command_id": "cmd-example",
  "device": "esp32-lab-sensor",
  "success": true,
  "data": {"parameter": "relay", "value": true}
}
```

Для произвольной операции используйте `data.command: "invoke"`, ID действия
из `schema.actions` и объект `data.arguments`. В ответе укажите ID действия в
`data.action`. Командный обработчик текущей прошивки в
`esp32/examples/led/src/main.cpp` — рабочий пример приёма `set` и `invoke`, передачи
результата и защиты от повторного выполнения через `command_id`.

### Действия и ошибки

Действие сначала объявляется в `schema.actions`. Например, для
`"calibrate": {"label": "Калибровка", "arguments": {"offset": {"type": "number", "min": -5, "max": 5}}}`
команда будет такой:

```json
{
  "type": "command",
  "id": "cmd-calibrate",
  "device": "esp32-lab-sensor",
  "data": {
    "command": "invoke",
    "command_id": "cmd-calibrate",
    "action": "calibrate",
    "arguments": {"offset": 0.5}
  }
}
```

Успешный ответ содержит тот же `command_id`, `success: true` и
`data: {"action": "calibrate"}`. При ошибке отправьте `success: false` и текст
в **`data.error`**:

```json
{
  "type": "command_result",
  "id": "cmd-calibrate",
  "command_id": "cmd-calibrate",
  "device": "esp32-lab-sensor",
  "success": false,
  "data": {"action": "calibrate", "error": "Sensor is not ready"}
}
```

Для отказа `set` вместо `data.action` передайте `data.parameter` и фактическое
`data.value`, если оно известно. Положительное подтверждение параметра должно
содержать запрошенное и реально установленное значение. Несовпадающее
значение или неверный тип Gateway считает ошибкой. Отчёт `state` не заменяет
`command_result`; для завершения ожидающей команды нужен её ответ.

## Подтверждения и повторная доставка

Флаг `command_dedup` должен быть `true` только если прошивка действительно
сохраняет и повторно использует результат для каждого ID команды. Для
автоматических повторов также нужен `command_replay_guard: true`: прошивка
должна понимать `data.require_cached_result: true` и никогда не выполнять
неизвестный ID из такого запроса. Без обеих защит Gateway не повторяет
отправленную команду после потери подтверждения, чтобы не запустить действие
дважды. LED-пример и универсальная прошивка используют
общий `CommandResultCache` из `esp32/shared/lib/GatewayClient/src`: каждый
профиль хранит до 16 ID и их результаты в NVS. Транспорт
`GatewayClient` не включает кэш автоматически — прошивка явно резервирует
команду перед выполнением и сохраняет её результат перед подтверждением.

Для повторного `command_id` отправляйте сохранённый результат, не запускайте
действие заново. Хранение только в RAM не защищает от повторов после
перезапуска платы. Даже NVS-кэш не даёт абсолютной гарантии «ровно один раз»:
сбой питания между выполнением действия и сохранением результата оставляет
неопределённость. Без реализованного кэша объявляйте `command_dedup: false`.
Поставляемые профили объявляют `true` только после успешного открытия,
привязки к firmware ID и проверки сохранённых записей и доступности записи.

В обоих профилях перед любым действием сохраняется намерение выполнить команду.
Один слот — одна атомарная NVS-запись с ID, порядковым номером, результатом и
контрольной суммой. После выполнения та же запись заменяется результатом;
каждая запись проверяет `nvs_commit` и обратное чтение. Отдельного изменяемого
указателя кольца нет: после перезапуска он восстанавливается по порядковым
номерам. Повтор подтверждения не меняет GPIO и не начинает индикацию заново.
У такого ответа добавляется `replayed: true` на верхнем уровне, исходная
запись кэша не изменяется. Gateway завершает ожидающую команду её исходным
результатом, но не считает его текущим состоянием: после ответа прошивка
присылает отдельный актуальный `state`. Так повтор старого «включить» после
перезапуска не создаёт ложное новое включение и запуск автоматизации.

Если питание пропало между намерением и сохранением результата, прошивка
отвечает отрицательным ACK: результат неизвестен, действие не повторялось.
Оно могло успеть выполниться до сбоя. Проверьте текущее состояние, прежде чем
отправлять новую команду с новым ID. Это защита от опасного повтора, а не
гарантия выполнения «ровно один раз». Незавершённые намерения не вытесняются
новыми командами. Если все 16 слотов заняты такими намерениями, новые команды
отклоняются без действия и перезаписи старых ID; обычная перезагрузка их не
удаляет.

Завершённые результаты вытесняются по мере заполнения кольца. Поэтому Gateway
помечает повтор ранее отправленной команды `data.require_cached_result: true`.
Если результат сохранился, прошивка возвращает его. Если ID уже вытеснен или
кэш был очищен, приходит отрицательное подтверждение без нового действия.
Это действует и после перезапуска Gateway: число попыток хранится в его базе.
Для новой осознанной команды нужен новый ID; старые ID не следует использовать
повторно. Старые прошивки без `command_replay_guard` по-прежнему могут
подключаться, но автоматический повтор отправленных команд для них отключён.

Ошибка сохранения намерения запрещает действие. Ошибка сохранения результата
оставляет намерение в RAM и NVS: отправляется отрицательный ACK с сообщением,
что действие могло выполниться, и актуальный `state`. Успешный ACK при этом не
выдаётся; повтор в этой сессии получает сообщение о неизвестном результате.
Если запись успела сохраниться, но проверка вернула ошибку, после перезапуска
может восстановиться уже завершённая запись; её ответ помечается `replayed`.
Новые действия при ошибках записи, чтения или повреждённом кэше
отклоняются. На старте проверяется запись с обратным чтением, и только после
этого прошивка объявляет `command_dedup: true`. Диагностика выводится в Serial
Monitor; сначала устраните проблему NVS и перезапустите плату. Очистка NVS
удаляет защиту для старых ID: остановите ожидающие команды Gateway перед
осознанным сбросом. Успешные записи прежнего формата LED-примера мигрируют
автоматически; неполная или повреждённая пара ID/результата блокирует новые
действия, чтобы не повторить команду с неизвестным исходом. После проверенной
миграции удаляются только устаревшие LED-ключи `idN`, `rN` и `next`; новые
записи команд сохраняются. Прошивка со старым парным форматом после отката
не увидит обновлённый кэш: перед откатом завершите или отмените ожидающие команды, не полагайтесь
на защиту старых ID в прежней версии.

LED использует namespace `command_ack_v2`, universal — `universal_ack`.
Namespace привязан к firmware ID: изменение только отображаемого имени или
Gateway ID эту привязку не меняет. Другой firmware ID в существующем namespace
блокирует команды, чтобы не использовать подтверждения чужого устройства.
Чтобы сознательно сменить firmware ID той же платы, сначала завершите или
отмените ожидающие команды прежнего ID в Gateway. Затем задайте новый
namespace кэша в вызове `begin()` либо отдельно сбросьте прежний namespace
средствами NVS. Обычное переименование устройства в Gateway этого не требует.
Прежние ID команд после такого сброса нельзя использовать для повторной
доставки; общий сброс NVS также удаляет аппаратную конфигурацию universal.
Кэш команд отделён от аппаратной конфигурации `device_cfg`; применение
конфигурации защищено собственными `config_version`/`config_hash` и не занимает
слоты команд.

В собственной прошивке подключите `<CommandResultCache.h>` и создайте один
экземпляр. В `setup()` вызовите `begin(DEVICE_ID, "my_command_ack")` с отдельным
namespace до 15 символов. В `hello` передайте `available()` в `command_dedup`
и `command_replay_guard`. Обрабатывая команду, сначала проверьте адрес,
`validCommandId(...)` и необязательный булевый `data.require_cached_result`,
затем вызовите `reserve(id, replay, !requireCachedResult)`: только
`Decision::Execute` разрешает действие. `Replay` отправляет
готовый ответ `replay`, а `Uncertain`/`Rejected` требуют отрицательного ACK
без выполнения. После нового выполнения передайте `command_result` как
`JsonDocument` в `complete(result, outgoing)` и отправьте непустой `outgoing`.
При `false` метод формирует отрицательное подтверждение, а при невозможности
сериализации оставляет `outgoing` пустым; самостоятельно
отправлять исходный успешный результат нельзя. После повтора и ошибки
отправляйте актуальный `state`. Третий аргумент `begin(..., true)` предназначен
только для миграции namespace LED-примера, обычному новому профилю он не нужен.

Регрессия кэша запускает его настоящий C++-код с памятью вместо NVS и
искусственными сбоями записи/чтения, перезапуском и потерей результата:

```powershell
python -m unittest gateway.tests.test_firmware_command_cache -v
```

Нужен host-компилятор `g++` или `clang++` в PATH либо путь к нему в переменной
`CXX`; также поддерживается путь к portable Zig в `ZIG`. Без компилятора
проверка явно пропускается. Дополнительный тест адаптера использует настоящий
ArduinoJson из `.pio/libdeps` после сборки профиля либо из каталога
`ARDUINOJSON_INCLUDE_DIR`. Без этих заголовков пропускается только тест
адаптера. Он проверяет отдельные namespace, привязку к ID, отрицательные ACK,
миграцию и очистку прежних ключей, используя заглушки NVS/Arduino.
Это не проверка GPIO или
физической flash-памяти: сбой питания и переподключение с реальной платой
проверяются отдельно, без подключения исполнительных устройств к нагрузке.

## Добавление собственного датчика

Например, в скопированном LED-проекте можно добавить сырой ADC-вход на GPIO 4.
Это пример для аналогового источника сигнала, а не для DS18B20.
В `buildDeviceSchema()` после создания объекта `parameters`:

```cpp
JsonObject sensor = parameters["light_raw"].to<JsonObject>();
sensor["label"] = "Аналоговый вход";
sensor["type"] = "integer";
sensor["access"] = "read_only";
sensor["unit"] = "raw";
sensor["min"] = 0;
sensor["max"] = 4095;
```

В `setup()` задайте `pinMode(4, INPUT)` и `analogReadResolution(12)`.
В `sendState()` после создания `parameters` добавьте:

```cpp
parameters["light_raw"] = analogRead(4);
```

Увеличьте `schema_version` в `sendHello()`, загрузите изменённую прошивку и
примите новую Schema. Вход появится в карточке и Blockly. Обработчик `set`
для него не нужен, поскольку параметр только для чтения. Выберите GPIO по
распиновке своей платы; `raw` — отсчёты ADC, а не люксы. Для физических единиц
нужны формула и калибровка: тогда меняются и значение, и `unit`/диапазон Schema.

При добавлении управляемого параметра также расширьте обработчик `set`.
При добавлении действия расширьте `invoke`. При изменении состояния своим
алгоритмом отправляйте `state`, даже если команда от Gateway не приходила.

Для DS18B20 в собственной прошивке нужны OneWire/DallasTemperature и код
конверсии, а в Schema — `number`, `read_only`, единица `°C` и реальный диапазон.
Вызов `analogRead()` этот цифровой датчик не считывает. Реализацию с
асинхронной конверсией и обработкой ошибок можно изучить в
[`UniversalDevice.cpp`](../esp32/universal/src/UniversalDevice.cpp), а подключение —
в [разделе DS18B20](UNIVERSAL_FIRMWARE.md#ds18b20-на-esp32-c3-и-esp32-s3).
При своём C++ вы сами выбираете поддерживаемые датчики и библиотеки;
GPIO и алгоритм задаёт код, поэтому для него не нужен аппаратный конструктор
универсальной прошивки в браузере.

С дисплеем или другим модулем порядок тот же: подключите библиотеку его
контроллера в `platformio.ini`, инициализируйте её в `setup()` и обновляйте
короткими шагами. Например, режимы `clock` и `temperature` выбирают алгоритм
отрисовки, enum-параметр сообщает текущую страницу, а `show_message` может
быть обычным действием со строковым аргументом. Все они используют прежние
Schema/`state`/`command_result`; сам Gateway не рисует экран и не знает
электрический протокол подключённого дисплея.

## Режимы устройства

### Готовый пример: ручное управление и мигание

LED-пример объявляет два режима:

| ID | Название | Поведение |
| --- | --- | --- |
| `manual` | Ручной | Постоянный свет определяется параметром `led` |
| `blink` | Мигание | Фаза меняется каждые 500 мс; полный цикл занимает секунду |

После старта выбран ручной режим, LED выключен. Выбор «Мигание» включает
`led` и запускает алгоритм на плате. При этом `led: true` означает, что
работа индикатора разрешена, а `blink_active: true` объясняет его мигающее
поведение. Каждая физическая фаза не превращается в отдельное изменение
параметра `led`: это не засоряет историю событиями каждые полсекунды.

- Выбор «Ручной» прекращает мигание и сохраняет логическое Вкл/Выкл.
- Установка `led` вручную всегда выбирает ручной режим; `led: false`
  действительно выключает LED, включая общую команду выключения Gateway.
- Отключение активного `blink` возвращает ручной режим с выключенным LED.
  Повторное отключение уже неактивного `blink` ничего не меняет.
- «Найти устройство» временно показывает свою индикацию, затем возвращает
  текущий вывод выбранного режима.
- Переподключение к Gateway не сбрасывает алгоритм. Перезапуск самой платы
  возвращает ручной режим/выключено: выбор режима в этом примере не хранится
  в NVS. Для своего устройства сохранение можно реализовать отдельно.

Сохранённые серверные сценарии тоже отправляют обычные команды. Если уже есть
автовыключение `led` через пять секунд, включение мигания может запустить его;
пришедший `led: false` остановит мигание. Это согласованное поведение двух
алгоритмов. Для проверки автономного режима временно отключите конфликтующие
сценарии либо предусмотрите в них проверку `blink_active`.

### Как объявить режим явно

Реестр в `src/DeviceModes.cpp` связывает стабильные ID с настоящими
обработчиками из `LedModes.h/.cpp`. Ниже запись из рабочего примера;
общую реализацию реестра ниже неё сохраняют:

```cpp
#include "DeviceModes.h"
#include "LedModes.h"

const char* const MANUAL_CONFLICTS[] = {"blink", nullptr};
const char* const BLINK_CONFLICTS[] = {"manual", nullptr};

const DeviceModeRegistration deviceModes[] = {
    {"manual", "Ручной", "Постоянный свет управляется параметром LED.",
     MODE_CAN_SELECT, selectManualLedMode, nullptr, nullptr,
     MANUAL_CONFLICTS, "manual_active", true, manualLedModeIsActive},

    {"blink", "Мигание", "Неблокирующее мигание индикатора.",
     MODE_CAN_SELECT | MODE_CAN_ENABLE | MODE_CAN_DISABLE,
     enableBlinkLedMode, enableBlinkLedMode, disableBlinkLedMode,
     BLINK_CONFLICTS, "blink_active", true, blinkLedModeIsActive},

    {nullptr, nullptr, nullptr, 0, nullptr, nullptr, nullptr, nullptr,
     nullptr, false, nullptr}
};
```

Поля каждой записи по порядку:

| Поле C++ | Смысл |
| --- | --- |
| `id`, `label`, `description` | Стабильный ID, название и описание |
| `operations` | Комбинация флагов разрешённых операций |
| `select`, `enable`, `disable` | Функции `bool handler(String& error)`; `nullptr`, если операции нет |
| `conflictsWith` | Массив ID других режимов с завершающим `nullptr` |
| `statusParameter`, `statusValue` | По какому параметру и значению режим считается активным |
| `isActive` | Функция `bool handler()`, сообщающая действительную активность режима |

`MODE_CAN_SELECT`, `MODE_CAN_ENABLE`, `MODE_CAN_DISABLE` включают только
операции с существующим обработчиком. Функция возвращает `true`, когда
переключение действительно выполнено, или `false` с объяснением в `error`.
Запуск длительного режима подтверждается сразу после успешного выбора;
ожидать завершения всего алгоритма в обработчике не нужно.

`appendRegisteredDeviceModes()` автоматически добавляет `schema.modes`,
соответствующие `schema.actions` и read-only boolean-параметры статуса:

| Операция | Созданный ID действия |
| --- | --- |
| Выбрать `manual` | `mode_manual_select` |
| Выбрать `blink` | `mode_blink_select` |
| Включить `blink` | `mode_blink_enable` |
| Выключить `blink` | `mode_blink_disable` |

Не объявляйте другое действие с таким же ID вручную. Для собственных режимов
используйте ID длиной 1–47 символов: латинская буква, затем буквы, цифры,
`_`, `.` или `-`. Не меняйте ID без необходимости: сохранённые команды и
сценарии ссылаются на них.

В `sendState()` уже вызывается `appendRegisteredDeviceModeStates(parameters)`.
Gateway получает `manual_active` и `blink_active`, поэтому может показать,
какой режим активен. Используйте отдельный status-параметр каждого режима;
имя `led` для статуса брать нельзя — оно уже описывает другое состояние.
Для обычного случая задайте `statusValue=true`, а `isActive()` пусть возвращает
активность именно этого режима. Метаданные `conflicts_with` описывают
несовместимость, но настоящее взаимное исключение реализуют обработчики ESP32.

В `statusParameter` используйте такие же короткие латинские ID реестра,
например `night_active`; произвольное имя переменной C++ не публикуется само.

В реестре до восьми режимов; завершающая пустая запись остаётся последней.
Чтобы совсем убрать режимы, оставьте только её. Флаги здесь описывают API,
а не являются командами от Gateway сами по себе.

### Где находится алгоритм

В `LedModes.cpp` находятся флаг активности, фаза и время последнего шага.
`initializeLedModes(setLedOutput)` связывает алгоритм с логическим выходом
приложения. `updateLedModes(millis())` вызывается из обычного `loop()` независимо
от наличия Gateway; физический выход обновляется с учётом индикации поиска.
Тело неблокирующего шага в этом файле выглядит так:

```cpp
bool updateLedModes(uint32_t now) {
    if (!blinking) return false;
    const uint32_t elapsed = now - lastPhaseAt;
    if (elapsed < BLINK_INTERVAL_MS) return false;
    const uint32_t steps = elapsed / BLINK_INTERVAL_MS;
    lastPhaseAt += steps * BLINK_INTERVAL_MS;
    if ((steps & 1U) == 0) return false;
    blinkPhase = !blinkPhase;
    return true;
}
```

Переменные объявлены в том же исходнике; `true` у этого шага означает
изменение физической фазы. Это отдельная функция от командного callback,
у которого `true` означает успешное выполнение операции. Такой шаг быстро
возвращает управление, в том числе при задержке цикла и переполнении `millis()`.

Для своего вентилятора, экрана или режима датчика замените аппаратную логику
в отдельном модуле и зарегистрируйте его обработчики. Если нужны настройки
режима — период, скорость, текст — объявите их обычными параметрами
`read_write` или отдельными действиями с аргументами. Текущий
`DeviceModeHandler` принимает только `String& error`; аргументы команды
в callback режима автоматически не передаются.

### Если список режимов пуст

Проверьте, что вы загрузили собственную прошивку с заполненным `deviceModes`,
а `buildDeviceSchema()` вызывает `appendRegisteredDeviceModes(schema)`.
У записи должны быть корректный ID, флаг операции и соответствующий callback.
Увеличьте `schema_version`, переподключитесь и примите новую Schema в Gateway:
при сохранении прежней Schema новые режимы в интерфейс не попадут. Неверные
регистрации диагностируются в Serial строкой `[MODE]`.

## Обновление Schema и проверка прошивки

Для общей кнопки выключения объявите явную операцию
`schema.common_commands.off`: например, установку параметра `led` в `false`
или вызов своего действия остановки. LED-пример уже содержит это назначение.
Gateway проверяет его по Schema; пользователь может изменить назначение
для своей установки. Формат и границы поведения описаны в
[DEVICE_GROUPS.md](DEVICE_GROUPS.md).

Для обычной прошивки достаточно передавать актуальную Schema в каждом
`hello`. Gateway сравнивает её по содержимому и повторно предлагает изменения
при следующем подключении, если пользователь оставил прежнюю версию.
Сообщение `schema_update` поддерживается для смены Schema без переподключения,
но не является обязательной частью обычного запуска.

Проверьте после изменения: первый допуск и повторное подключение, полный
`state` после ACK, типы и единицы, ручную команду и её отказ, повтор
`command_id` при включённом dedup, сценарий с паузой и восстановление связи.
Входящая Schema ограничена 60 КиБ, всё WebSocket-сообщение — 64 КиБ.
Численные ограничения параметров и действий перечислены в
[справочнике Schema](DEVICE_SCHEMA.md).

Физический индикатор не обязателен. Объявляйте `capabilities.identify` и
`actions.identify` только при наличии реализованного способа поиска устройства;
метаданные сами по себе светодиод не включат. Диагностика общих Wi-Fi и
WebSocket-логов описана в
[руководстве универсального профиля](UNIVERSAL_FIRMWARE.md#связь-и-диагностика-переподключений).

## Выбор профиля и границы реализации

`GatewayClient` переиспользуется пользовательской прошивкой и переносит
Wi-Fi, WebSocket, повторное подключение и отправку JSON в отдельную библиотеку.
Пользовательская прошивка сама объявляет Schema и реализует действия и режимы.
Для обычной настройки GPIO без собственного кода есть отдельный проект
[`esp32/universal`](../esp32/universal) и руководство
[`UNIVERSAL_FIRMWARE.md`](UNIVERSAL_FIRMWARE.md). Он поддерживает ограниченный
реестр драйверов, принимает аппаратную конфигурацию, проверяет её, сохраняет
в NVS и отправляет подтверждение с актуальной Schema. Новые типы датчиков
нельзя включить одной записью в веб-конструкторе: необходимо реализовать
драйвер в прошивке и соответствующую серверную проверку.
