# Пользовательская прошивка ESP32

Пользовательская прошивка отвечает за датчики, исполнительные механизмы и
собственные алгоритмы устройства. `GatewayClient` берёт на себя подключение к
Wi-Fi и WebSocket Gateway; Schema и смысл команд задаёт прошивка.

## Подключение библиотеки

Библиотека уже подключена к основной прошивке PlatformIO. Отдельный пример
пользовательской прошивки расположен в `esp32/examples/advanced_gpio_led`;
его `platformio.ini` использует общую библиотеку из `esp32/lib/GatewayClient`.
Для другого проекта скопируйте каталог `GatewayClient` в его каталог `lib`.
Библиотека объявляет зависимости WebSockets и ArduinoJson в `library.json`.

В рабочем профиле код разделён по ответственности:

- `GatewayClient` — Wi-Fi, WebSocket, переподключение и JSON-транспорт;
- `esp32/src/main.cpp` — запуск, телеметрия и обработчики команд конкретного
  устройства;
- `esp32/src/DeviceSchema.cpp` — описание параметров и возможностей;
- `esp32/src/DeviceModes.cpp` — реестр режимов и их обработчики;
- `esp32/include/device_config.h` и локальный `secrets.h` — ID, профиль платы
  и настройки подключения.

В собственном проекте можно сохранить такое же разделение или объединить
файлы, если проект небольшой. Не добавляйте Wi-Fi-пароль в публикуемые файлы.

Создайте локальный `secrets.h` с параметрами сети:

```cpp
#pragma once
#define WIFI_SSID "имя Wi-Fi"
#define WIFI_PASSWORD "пароль Wi-Fi"
#define GATEWAY_IP "192.168.0.102"
```

Рабочий пример регистрирует устройство `esp32-advanced-01`, объявляет
управляемый параметр `led`, принимает команды и отправляет подтверждения.
Он рассчитан на ESP32-S3 с обычным LED на GPIO 48. Скопируйте
`esp32/include/secrets.example.h` в `esp32/include/secrets.h`, укажите Wi-Fi,
затем соберите пример:

```powershell
pio run -d esp32/examples/advanced_gpio_led
```

Чтобы прошить плату, добавьте `-t upload`. Для другой платы измените пин и
драйвер под её схему. Этот пример демонстрирует обычный GPIO LED; NeoPixel
требует соответствующего драйвера.

В собственном обработчике `WStype_CONNECTED` отправляйте `hello`. Например,
светочувствительный датчик может объявить числовой параметр `illuminance` с
доступом `read_only` и единицей `lx`. Затем прошивка отправляет `state` с
текущим `data.parameters.illuminance`; Gateway проверяет Schema и показывает
значение в устройстве и блоках автоматизации.

## Формат сообщений

Регистрация устройства — сообщение `hello` с уникальным ID и Schema:

```json
{
  "type": "hello",
  "device": "esp32-lab-sensor",
  "name": "Датчик в мастерской",
  "protocol_version": 2,
  "firmware_version": "1.0.0",
  "schema_version": 1,
  "command_dedup": false,
  "schema": {
    "format_version": 1,
    "parameters": {
      "illuminance": {
        "label": "Освещённость",
        "type": "number",
        "access": "read_only",
        "unit": "lx"
      },
      "relay": {
        "label": "Реле",
        "type": "boolean",
        "access": "read_write",
        "control": "toggle"
      }
    },
    "actions": {}
  }
}
```

Идентификатор `device` задаётся латиницей и должен быть уникальным. `name` —
отображаемое пользователю имя и может быть русским. Увеличивайте
`schema_version`, когда меняется объявленная Schema. Gateway всё равно
сравнивает содержимое Schema, а не полагается только на номер версии.

Gateway отправляет команду параметра так:

```json
{
  "type": "command",
  "id": "cmd-example",
  "device": "esp32-lab-sensor",
  "data": {
    "command": "set",
    "command_id": "cmd-example",
    "parameter": "relay",
    "value": true
  }
}
```

После фактического выполнения прошивка отвечает `command_result`, указав то
же значение, которое удалось применить:

```json
{
  "type": "command_result",
  "id": "cmd-example",
  "command_id": "cmd-example",
  "device": "esp32-lab-sensor",
  "success": true,
  "data": {"parameter": "relay", "value": true}
}
```

Для произвольной операции используйте `data.command: "invoke"`, ID действия
из `schema.actions` и объект `data.arguments`. В ответе укажите ID действия в
`data.action`. Командный обработчик текущей прошивки в
`esp32/src/main.cpp` — рабочий пример приёма `set` и `invoke`, передачи
результата и защиты от повторного выполнения через `command_id`.

Флаг `command_dedup` должен быть `true` только если прошивка действительно
сохраняет и повторно использует результат для каждого ID команды. Без этой
защиты Gateway не повторяет команду после потери подтверждения, чтобы не
запустить действие дважды. Реализация ESP32 хранит последние 16 результатов в
NVS; библиотека `GatewayClient` намеренно не подменяет эту логику.

## Режимы устройства

Сложные режимы остаются в пользовательской прошивке. Зарегистрируйте их в
`esp32/src/DeviceModes.cpp`: общий код добавит операции режима в Schema и
направит команды соответствующим обработчикам. Допустимые операции
`select`, `enable` и `disable` ссылаются на ID этих действий. При необходимости
режим может ссылаться на параметр состояния и перечислить конфликтующие
режимы. Gateway проверит ссылки и отобразит доступные операции в карточке
устройства и автоматизациях. Подробный пример структуры реестра обработчиков
приведён в [`AUTOMATION.md`](AUTOMATION.md#действия-и-прошивочные-режимы).

## Выбор профиля и границы реализации

`GatewayClient` переиспользуется пользовательской прошивкой и переносит
Wi-Fi, WebSocket, повторное подключение и отправку JSON в отдельную библиотеку.
Пользовательская прошивка сама объявляет Schema и реализует действия и режимы.
Для обычной настройки GPIO без собственного кода есть отдельный проект
[`esp32/universal`](../esp32/universal) и руководство
[`UNIVERSAL_FIRMWARE.md`](UNIVERSAL_FIRMWARE.md). Он поддерживает ограниченный
реестр драйверов, принимает аппаратную конфигурацию, проверяет её, сохраняет
в NVS и отправляет подтверждение с актуальной Schema. Новые типы датчиков
нельзя включить одной записью в веб-конструкторе: необходимо реализовать
драйвер в прошивке и соответствующую серверную проверку.
